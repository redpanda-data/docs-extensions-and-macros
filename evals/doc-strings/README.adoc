= Doc-strings evals: execution-verified model behaviors
:toc:
:toc-placement!:

Evals for the four MODEL-DRIVEN behaviors that the doc-strings GitHub
workflows delegate to Claude. The deterministic tools themselves
(`tools/lint-strings`, `tools/preview-string`, `tools/overrides-audit`) are
covered by the jest suite and are NOT re-tested here - they are the
*measuring instruments* these evals use to grade the model.

toc::[]

== The philosophy: execute, never grade prose

The failure mode this harness exists to avoid: evals whose assertions are
regex matches over model prose. Those pass without exercising anything and
cannot meaningfully fail.

Every verdict here is computed by *executing* the model's output against the
real machinery:

1. A fixture mini-repo (shaped like redpanda: `src/v/config/`, `*probe.cc`,
   `src/go/rpk/pkg/cli/`) is materialized in a temp dir.
2. The real tools produce the genuine input the production workflow would
   feed the model (`doc-tools lint-strings --format json` findings, or a
   `doc-tools overrides audit` candidate row).
3. For the review's own behaviors (rewrite, prose quality, false-positive
   guard), the model runs the *production* review: the prompt, allowed and
   disallowed tools, MCP servers and turn limit of the "Claude review with
   suggestions" step in `doc-strings-review.yml` at this commit, on Opus 5,
   the model streaming-enterprise and redpanda-operator pass (see
   `production.js`). The workspace gets the files the workflow writes before
   that step: `lint-findings.json`, `pr-diff.patch`, and the writing standard
   and terminology fetched from docs-team-standards. The one stand-in is the
   GitHub inline-comment tool (`mocks/inline-comment.js`), which records each
   comment instead of posting it. The upstream-port and audit behaviors,
   whose production prompts do not live in this repo, use the templates in
   `prompts.js` (`claude -p`, no tools, 300s timeout).
4. The harness *applies* the output - each recorded comment's
   `+```suggestion+` block replacing the finding's `line_start..line_end`, or
   a `LINES a-b` + `+```replacement+` span edit - to the fixture file. A
   `doc-impact.json` the review writes is checked with the workflow's own
   dispatch predicate.
5. The verdict is re-computed mechanically:
   * re-run `lint-strings`: the rewritten declaration must have **zero
     findings of any severity**, and every untouched declaration must keep
     exactly the findings it had (fingerprint compare);
   * re-run the surface extractor (the real Python property extractor, the
     metrics scanner, the rpk scanner): the target must still parse, every
     other declaration must be byte-identical, and every non-description
     field of the target must be unchanged;
   * for upstream ports, re-run `overrides audit`: the classification must
     flip (`UPSTREAMABLE -> REDUNDANT`, `SPLIT -> KEEP`), which is the
     production definition of "the port worked";
   * blanked-literal structural compare: string-literal contents are
     blanked, adjacent literals merged, whitespace neutralized - the result
     must be identical before/after, proving the model changed *no token
     outside the doc string* while still allowing clang-format re-wrapping;
   * C++ suggestions must keep every line within 80 columns.

No check ever asks "does the model's answer *sound* right". The only prose
inspection anywhere is fence parsing and, for the audit control, the literal
`NO_SUGGESTIONS` sentinel - both structural. The review's own negative
control passes only when the production review posts no inline comment and
writes no `doc-impact.json`.

== Why the review cases run the production prompt

The review's prompt lives in this repo on purpose: callers pin the workflow
by SHA, so a prompt change reaches an engineering repo only through a
reviewed pin bump (see `CLAUDE.md`). The eval reads the prompt from the same
file, so a passing run is a statement about exactly what a pin bump ships.
Never reintroduce a hand-written copy of the review prompt here. The copy
that used to live in `prompts.js` shared no rule sentence with the shipped
prompt by the time it was replaced, and its negative control passed on a
string the real review flags (a restated concrete default).

== The four behaviors under test

[cols="1,2,3"]
|===
|Behavior |Production home |Eval cases

|A. Suggestion rewrite
|`doc-strings-review.yml` (redpanda, redpanda-operator): Claude turns
deterministic lint findings into GitHub suggestion blocks
|`prop-empty-description`, `prop-tautology-no-period`, `metric-name-echo`
(rewrite must carry NO terminal period), `rpk-flag-lowercase-period` (only
the usage literal may change - the rest of the line is byte-compared)

|B. Upstream port
|`upstream-doc-strings.yml`: Claude ports override prose into the C++
source string it masks. NOT YET BUILT - no such workflow exists in this repo
or the docs repo, so behavior B is currently exercised only by these evals.
The evals are the contract the workflow will have to meet.
|`upstream-clean` (UPSTREAMABLE text lands verbatim), `upstream-split`
(SPLIT candidate: stripped prose lands, the xref must NOT reappear -
`detectDocsMarkup` over the re-extracted string must be empty)

|C. False-positive guard
|Both workflows' suggest-only posture
|`negative-property-diff` (conforming rewording diff -> zero suggestions,
zero doc-impact claims), `negative-metrics-file` (conforming probe file ->
the model must claim `{"findings": []}`). *Any* invention fails the case.
`unchanged-lines-kept` (rpk help text from streaming-enterprise PR 461 with
a few changed paragraphs: any suggestion must keep every unchanged line
byte-identical; its control runs the prompt with the changed-lines rule
reverted)

|D. Prose quality
|`doc-strings-review.yml`'s prose-quality pass (added in #297): the Claude
pass is gated on declarations the PR TOUCHED, not on lint findings, because
a string can satisfy every mechanical rule and still tell an operator
nothing.
|`prose-vacuous-clean` (a lint-clean but vacuous rewording: the model must
suggest a rewrite that restores substance, and the applied result must still
lint clean), `terminology-misuse` (a lint-clean, substantive description that
lowercases the product name, which `terminology.md` names as incorrect: the
model must suggest the canonical casing). Both sabotage against the fully
conforming rewording `negative-property-diff` uses, where staying silent is
correct and so fails the must-suggest check.
|===

== Negative controls that provably can fail

A negative control that cannot fail is decoration. `--sabotage <id>` re-runs
a negative control against a deliberately violating fixture (defined per
case as `sabotageEdits`), skips the zero-findings precondition, and *expects
the case to FAIL*:

[source,bash]
----
node evals/doc-strings/run-evals.js --sabotage negative-property-diff
node evals/doc-strings/run-evals.js --sabotage negative-metrics-file
node evals/doc-strings/run-evals.js --sabotage unchanged-lines-kept
----

A case can sabotage the prompt instead of the fixture: `sabotagePromptEdits`
puts back the text a rule replaced, so the control runs the production
prompt without that rule. Each edit must match the shipped prompt exactly
once, and a jest test checks that, so rewording the rule without updating
its control fails CI instead of running a control that proves nothing.

Exit 0 means the proof succeeded (the model flagged the planted violation
and the harness caught it as a FAIL verdict); exit 1 means the harness can
no longer catch invented findings and must be fixed. Nothing is edited on
disk, so there is nothing to restore afterwards.

Both proofs were run against the live model when this harness landed; both
controls demonstrably fail on violating input.

== Running

[source,bash]
----
npm run eval:doc-strings                     # full suite (11 cases)
node evals/doc-strings/run-evals.js --case metric-name-echo
node evals/doc-strings/run-evals.js --model sonnet   # override the production model
node evals/doc-strings/run-evals.js --keep-temp   # keep fixture repos
----

Without `--model`, review cases run on Opus (production) and the template
cases on Sonnet. Pass `--model` only for a deliberate comparison: a result on
any other model says nothing about what callers run.

Requirements:

* The `claude` CLI on PATH and authenticated. When it is missing the suite
  prints `SKIPPED` and exits with code 3 - a skipped run never looks green.
* `gh` authenticated with read access to redpanda-data/docs-team-standards,
  for the writing standard and terminology the workflow fetches. A failed
  fetch is a `HARNESS_ERROR`, never a review run without the standard.
* `jq`, for the dispatch predicate.
* The property-extractor venv (`tools/property-extractor/tmp/...`). It is
  created automatically on the first properties run (see
  `tools/lint-strings/surfaces/properties.js`).

Exit codes: `0` all pass (or sabotage proven), `1` failures, `2` harness
error, `3` skipped.

Deliberately **not wired into CI**: a full run makes eleven real model calls
(a few minutes of wall time and real tokens). Run it when the workflow
prompts, the lint rules, or the extraction change.

Each run writes `results/<timestamp>/<case>/` with the exact prompt, the raw
model output, before/after fixture snapshots, and `evidence.json` (every
mechanical check with its measured detail). `results/` is gitignored.

== Anatomy

[cols="1,3"]
|===
|`run-evals.js` |Driver + per-kind executors (rewrite, upstream,
negative-review, negative-audit). CommonJS, zero new dependencies.
|`cases.js` |Declarative case table. Every positive case pins
`expectRules` / `expectClassBefore` preconditions that are asserted against
the REAL tool output before the model is called - fixture drift aborts as
`HARNESS_ERROR` instead of silently testing something else.
|`production.js` |Runs the production review step from
`doc-strings-review.yml`: its prompt with Actions expressions filled (an
unknown expression is an error), its tool lists and turn limit, the inline
comment stand-in, and the workspace files the workflow writes.
|`mocks/inline-comment.js` |Stdio MCP server with the production tool name,
`create_inline_comment`, that appends each call to a log instead of posting.
|`prompts.js` |Templates only for behaviors whose production prompt lives
elsewhere (the docs repo's `upstream-doc-strings.yml`) and the audit control.
Never a copy of the review prompt.
|`lib.js` |Fixture materialization, real doc-tools invocations, fence
parsing, and the mechanical comparators (blanked-literal normalization,
extraction diffing, finding fingerprints).
|`fixtures/conforming_probe.cc` |Fully conforming metrics file for the
negative control. The harness asserts its zero-findings precondition on
every run, so drift cannot silently blunt the control.
|===

Fixture mini-repos are copied from `tools/lint-strings/fixtures/` (the same
known-bad/conforming sources the jest suite pins) and edited per case with
exact-match `find`/`replace` pairs that throw when they no longer match.

== Adding a case

1. Add an entry to `cases.js`:
   * `rewrite` kind: pick (or `edits`-create) a declaration in a fixture
     that the real linter flags, set `target` and `expectRules`, and for Go
     one-liners set `singleLine: true` (enables the byte-identical
     prefix/suffix check).
   * `upstream` kind: provide the `overrides` document, `expectClassBefore`
     (what the real audit must say going in) and `expectClassAfter` (what it
     must say after a correct port).
   * negative kinds: provide a conforming fixture (or `diffEdits`) AND
     `sabotageEdits` that plant a violation - a negative control without a
     sabotage path is not accepted, because it cannot prove it can fail.
2. Run the single case: `node evals/doc-strings/run-evals.js --case <id>`.
3. If it is a negative control, prove it: `--sabotage <id>` must exit 0.

Iteration rule (the honest-eval contract): when a positive case fails on a
legitimate model shortcoming, tighten the *prompt template* - that is the
eval doing its job of hardening the production prompt. Never weaken a
mechanical assertion to make a case pass. Comparator changes are only
acceptable when the assertion was measuring something the contract
explicitly permits (for example, clang-format re-wrapping), and must keep
every genuine token change failing.
