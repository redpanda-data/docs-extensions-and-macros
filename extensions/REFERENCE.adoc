== Add Bloblang samples to pages

The `collect-bloblang-samples` extension processes Bloblang examples from YAML files in the `examples` directory of the `redpanda-connect` component. This extension ensures that these examples are accessible as structured data for use in UI components or documentation, such as sample dropdowns in a Bloblang playground.

It validates, sorts, and attaches the processed examples as a JSON object to the Antora page attributes. The extension ensures examples have unique titles, mandatory fields (`input` and `mapping`), and are sorted in alphabetical order.

The processed examples are added as JSON to the `page-bloblang-samples` attribute. For example:

[,json]
----
{
  "hello-world.yaml": {
    "title": "Hello world",
    "input": "{\n  \"message\": \"hello world\"\n}\n",
    "mapping": "root.message = this.message.uppercase()\n"
  },
  "array-processing.yaml": {
    "title": "Array processing",
    "input": "{\n  \"numbers\": [1, 2, 3, 4, 5]\n}\n",
    "mapping": "root.even_numbers = this.numbers.filter(n -> n % 2 == 0)"
  }
}
----

=== Environment variables

This extension does not require any environment variables.

=== Configuration options

To enable the extension, add it to your Antora playbook under the `antora.extensions` key. No additional configuration is required.

[,yaml]
----
antora:
  extensions:
    - require: '@redpanda-data/docs-extensions-and-macros/extensions/collect-bloblang-samples'
----

=== Example Bloblang YAML file

The following YAML file is an example of how to define a Bloblang sample:

[,yaml]
----
title: Hello world
input: |
  {
    "message": "hello world"
  }
mapping: |
  root.message = this.message.uppercase()
----

== Add pages to root

The `add-pages-to-root` extension allows you to copy files from your Antora content catalog to the root of the site during the build process. This is particularly useful for files like `llms.txt` or any custom files that need to be directly accessible at the site's root level.

This extension processes a list of file paths provided in the playbook configuration, locates those files in the Antora content catalog, and adds them to the site's root directory during the publishing phase. Each file's content and basename are preserved in the process.

=== Environment variables

This extension does not require any environment variables.

=== Configuration options

Add the `add-pages-to-root` extension to your Antora playbook under the `antora.extensions` key, and specify the list of files to process in the `files` configuration.

[source,yaml]
----
antora:
  extensions:
    - require: '@redpanda-data/docs-extensions-and-macros/extensions/add-pages-to-root'
      files:
        - home:ROOT:attachment$custom-file.txt
----

=== Registration

[source,yaml]
----
antora:
  extensions:
    - require: '@redpanda-data/docs-extensions-and-macros/extensions/add-pages-to-root'
      files:
        - home:ROOT:attachment$custom-file.txt
----

== Algolia indexer

This extension generates an Algolia index for each version of each component. The index entries are then saved to Algolia using the `saveObjects()` method, and also saved as JSON files in the site catalog. JSON files are published to the site root using the template `algolia-<component>-<version>.json`.

NOTE: Only pages that include an `<article>` element with the `doc` class are indexed.

=== Environment variables

- `ALGOLIA_ADMIN_API_KEY` (required)
- `ALGOLIA_APP_ID` (required)
- `ALGOLIA_INDEX_NAME` (required)

=== Configuration options

The extension accepts the following configuration options:

excludes (optional)::
Any elements, classes, or IDs that you want to exclude from the index.
index-latest-only (optional)::
Whether to index all versions or just the latest version of a component.

=== Registration

```yaml
antora:
  extensions:
  - require: '@redpanda-data/docs-extensions-and-macros/extensions/algolia-indexer/index'
    excludes: ['.thumbs','script', '.page-versions','.feedback-section','.banner-container']
    index-latest-only: true
```

== Archive attachments

The `archive-attachments` extension automates the packaging of specific attachment files into a compressed archive (`.tar.gz`) based on configurable patterns. This archive is then made available to the generated site, allowing users to easily download grouped resources such as Docker Compose configurations.

This extension enables you to define which files and directories to include in the archive, ensuring that only relevant content is packaged and accessible.

=== Environment variables

This extension does not require any environment variables.

=== Configuration options

The extension accepts the following options in the Antora playbook.

Configure the extension in your Antora playbook by defining an array of archive configurations under `data.archives`. Each archive configuration includes:

output_archive (string, required):: The name of the generated archive file.

component (string, required):: The name of the Antora component whose attachments should be archived.

file_patterns (array of strings, required):: Glob patterns specifying which attachment paths to include in the archive.

NOTE: Ensure that `file_patterns` accurately reflect the paths of the attachments you want to archive. Overly broad patterns may include unintended files, while overly restrictive patterns might exclude necessary resources.

=== Example configuration

Here's an example configuration to enable the extension:

```yaml
antora:
  extensions:
    - require: '../docs-extensions-and-macros/extensions/archive-creation-extension.js'
      data:
        archives:
          - output_archive: 'redpanda-quickstart.tar.gz' <1>
            component: 'ROOT' <2>
            file_patterns:
              - '**/test-resources/**/docker-compose/**' <3>
```

<1> Defines the name of the generated archive placed at the site root.
<2> Defines the name of the component in which to search for attachments.
<3> Lists the glob patterns to match attachment paths for inclusion in the archive.
+
- `**`: Matches any number of directories.
- `/test-resources/`: Specifies that the matching should occur within the `test-resources/` directory.
- `/docker-compose/`: Targets the `docker-compose/` directory and all its subdirectories.
- `**:` Ensures that all files and nested directories within `docker-compose/` are included.

== Behavior with multiple components/versions

*Scenario*: Multiple components and/or multiple versions of the same component contain attachments that match the defined file_patterns.

*Outcome*: Separate archives for each component version.

For each matching (component, version) pair, the extension creates a distinct archive named `<version>-<output_archive>`. For example:
`24.3-redpanda-quickstart.tar.gz`.

These archives are placed at the site root, ensuring they are easily accessible and do not overwrite each other.

For the latest version of each component, the extension also adds the archive using the base `output_archive` name. As a result, the latest archives are accessible through a consistent filename, facilitating easy downloads without needing to reference version numbers.

Because each archive has a unique filename based on the component version, there is no risk of archives overwriting each other.
The only exception is the archive for the latest version, which consistently uses the `output_archive` name.

== Compute end-of-life extension

This extension calculates and attaches metadata related to the end-of-life (EoL) status of docs pages, such as nearing EoL, past EoL, and associated EoL dates. This metadata can be used to display relevant banners or messages in docs to inform users about the lifecycle of each version.

The extension leverages configuration settings provided in the Antora playbook to apply EoL calculations, specify the warning period, and include links to upgrade documentation and EoL policies.

The extension computes whether a page is nearing EoL or past EoL based on the `page-release-date` attribute and configured settings.
It injects the following attributes into each page, making them available for use in UI templates:

- `page-is-nearing-eol`: Indicates if the page is within the warning period before EoL. Calculated using `(page-release-date + supported_months) - warning_weeks`.
- `page-is-past-eol`: Indicates if the page has passed its EoL. Calculated using `today > (page-release-date + supported_months)`.
- `page-eol-date`: The calculated EoL date in a human-readable format. Calculated using `page-release-date + supported_months`.
- `page-eol-doc`: The URL to the supported versions policy or EoL documentation.
- `page-upgrade-doc`: The Antora resource ID to a document containing upgrade instructions.

=== Environment variables

This extension does not require any environment variables.

=== Configuration options

To enable and configure the extension, add it to the `antora.extensions` section of your Antora playbook. Define the EoL settings under the `data.eol_settings` key with the following options:

`component` (required):: The component name to which the configuration applies.
`eol_doc` (required):: A link to the supported versions policy or EoL documentation.
`upgrade_doc` (required):: A link to the upgrade instructions.
`supported_months` (optional, default: 12):: The number of months after the publish date when the documentation reaches its EoL.
`warning_weeks` (optional, default: 6):: The number of weeks before EoL when the documentation is considered to be nearing EoL. Can be used to decide when to notify users of the upcoming EoL status.

[,yaml]
----
antora:
  extensions:
    - require: '@redpanda-data/docs-extensions-and-macros/extensions/compute-end-of-life'
      data:
        eol_settings:
          - component: 'ROOT'
            supported_months: 18
            warning_weeks: 8
            eol_doc: https://support.redpanda.com/hc/en-us/articles/20617574366743-Redpanda-Supported-Versions
            upgrade_doc: ROOT:upgrade:index.adoc
----

=== Registration

You can register the extension with a customized configuration for different components in your playbook:

[,yaml]
----
antora:
  extensions:
    - require: '@redpanda-data/docs-extensions-and-macros/extensions/compute-end-of-life'
      data:
        eol_settings:
          - component: 'ROOT'
            supported_months: 12
            warning_weeks: 6
            eol_doc: https://example.com/supported-versions
            upgrade_doc: ROOT:upgrade:index.adoc
          - component: 'example-docs'
            supported_months: 24
            warning_weeks: 12
            eol_doc: https://example.com/example-supported-versions
            upgrade_doc: example-docs:upgrade:index.adoc
----


=== Example Handlebars template:

[,handlebars]
----
{{#if page.attributes.is-nearing-eol}}
  <div class="banner-container nearing-eol">
    This documentation will reach its end of life on {{page.attributes.eol-date}}.
    Please <a href="{{resolve-resource page.attributes.upgrade-doc}}">upgrade to a supported version</a>.
  </div>
{{else if page.attributes.is-past-eol}}
  <div class="banner-container past-eol">
    This documentation reached its end of life on {{page.attributes.eol-date}}.
    See our <a href="{{page.attributes.eol-doc}}" target="_blank">supported versions policy</a>.
  </div>
{{/if}}
----

== Generate index data

The `generate-index-data` extension creates structured index data about doc pages based on configurable filters. The indexed data is saved to a specified attribute in all component versions, enabling the dynamic generation of categorized links and descriptions within your docs using UI templates.

This extension allows you to define multiple indexing criteria, such as component, URL filter, and environment type.

The generated data is an array of objects, where each object represents a component version. Each object contains the following properties:

- `component` (string):
  The name of the Antora component.

- `version` (string):
  The version of the component.

- `pages` (array):
  A list of pages that match the indexing criteria. Each page contains:
** `title` (string): The title of the doc page.
** `url` (string): The URL of the doc page relative to the site root.
** `description` (string): A brief description sourced from the `:description:` attribute in the AsciiDoc file. Defaults to an empty string if not provided.

Example:

```json
[
  {
    "component": "ROOT",
    "version": "24.3",
    "pages": [
      {
        "title": "Manage Debug Bundles in Redpanda Console",
        "url": "/current/console/ui/generate-bundle/",
        "description": "Learn how to generate, download, and delete debug bundles in Redpanda Console for comprehensive cluster diagnostics."
      },
    ]
  }
]
```

=== Environment variables

This extension does not require any environment variables.

=== Configuration options

The extension accepts the following options in the Antora playbook.

NOTE: Ensure filters are well-defined to minimize unnecessary processing. Avoid overly broad configurations in `data.sets`.

- `data.sets` (required): An object defining one or more indexing configurations. Each configuration (or set) accepts the following options:

** `component` (string, required): The Antora component to search for pages.

** `attribute_name` (string, required): The attribute name to assign the generated index data. This allows pages and templates to reference the index.

** `filter` (string, optional): A substring to match within page URLs.

** `env_type` (string, optional): Matches pages with environment-specific attributes (for example, Docker, Kubernetes).

** `output_file` (string, optional): Save the generated index data as a JSON file at the specified path. If not provided, no file is created.

=== Example configuration

Here's an example configuration to enable the generate-index-data-extension:

```yaml
antora:
  extensions:
    - require: '@redpanda-data/docs-extensions-and-macros/extensions/generate-index-data-extension'
      data:
        sets:
          console_ui:
            component: ROOT  # Search the ROOT component
            filter: console/ui # Filter pages containing this substring in their URL
            attribute_name: console-ui-index # Save the result in this attribute
            output_file: redpanda-labs/console-ui-index.json # Save data to this file
          docker_labs:
            component: redpanda-labs
            filter: docker-compose
            env_type: Docker
            attribute_name: docker-labs-index
```

=== Use the generated data

The index data can be referenced in AsciiDoc pages by specifying the following required attributes:

```asciidoc
= CONSOLE UI
:page-index-data: console-ui-index <1>
:page-role: index-list <2>
```

<1> The attribute whose data you want to display on the page. This must match an attribute configured in the extension.
<2> The page role. This role specfies the UI template that renders the data in the `page-index-data` on the page.

You can optionally display pages only if they match the component and version of the current Asciidoc page by adding the `:page-match-component-version:` attribute.

```asciidoc
= CONSOLE UI
:page-index-data: console-ui-index
:page-role: index-list
:page-match-component-version: ''
```

== Redpanda Connect tag modifier

This extension updates the playbook to use the latest release tag for the Redpanda Connect documentation. It ensures that the Redpanda Connect documentation is always pulled from the latest release tag available on GitHub.

=== Environment variables

- `REDPANDA_GITHUB_TOKEN` (optional): A Personal access token (PAT) that has `repo` permissions for the `redpanda-data` GitHub organization.

NOTE: If you don't set the environment variable, the latest version of Redpanda Connect may not be fetched. When the environment variable is not set, the extension sends unauthenticated requests to GitHub. Unauthenticated requests may result in hitting the API rate limit and cause GitHub to reject the request. In this case the fallback version is used. This version is defined in the playbook where the extension is registered.

=== Configuration options

There are no configurable options for this extension.

=== Registration

```yaml
antora:
  extensions:
    - require: '@redpanda-data/docs-extensions-and-macros/extensions/modify-connect-tag-playbook'
```

== Version fetcher

This extension fetches the latest release versions from GitHub.

=== Attributes

The following attributes are available to all versions of all Antora components:

`latest-console-version`:: The latest release version of Redpanda Console.
`latest-connect-version`:: The latest release version of Redpanda Connect.
`redpanda-beta-version`:: The latest RC version of Redpanda.
`redpanda-beta-commit`:: The commit hash for the latest RC version of Redpanda.
`console-beta-version`:: The latest beta version of Redpanda Console.
`operator-beta-version`:: The latest beta version of the Redpanda Operator.
`helm-beta-version`:: The latest beta version of the Redpanda Helm chart.
`latest-operator-version`:: The latest release version of the Redpanda Operator. This value keeps its `v` prefix (for example, `v25.1.3`) because pages pass it straight to `helm --version`.
`latest-redpanda-helm-chart-version`:: The latest release version of the Redpanda Helm chart.

The following attributes are available to the latest version of each Antora component:

`full-version`:: The latest release version of Redpanda. Only ever moves forwards: if the component's `antora.yml` already pins a higher version, that pin wins.
`latest-redpanda-version`:: The latest release version of Redpanda.
`latest-release-commit`:: The commit hash for the latest release version of Redpanda.

==== Tag and short-version siblings

Most `<base>-version` attributes in the previous lists also get two siblings.
`full-version` is the exception and gets neither, because it is set directly
rather than through the shared helper, and it is the one attribute that only
ever moves forwards.

`<base>-tag`:: The version exactly as the release publishes it, including any `v` prefix (for example, `latest-redpanda-tag` is `v26.2.1`). Use this for container image tags and Git references. There is no tag attribute for `latest-operator-version` or `latest-redpanda-helm-chart-version`, which are already raw values.
`<base>-version-short`:: Only the `major.minor` part (for example, `latest-redpanda-version-short` is `26.2` when `latest-redpanda-version` is `26.2.1`). Use this where a page needs the release line rather than an exact patch, such as a download directory or an install pack name.

A short attribute is only set when a `major.minor` pair can be derived. Release channels that are not versions, such as `nightly` or `latest`, get a `-version` and a `-tag` but no `-version-short`, so a page never renders a fabricated release line.

==== Seed a fallback in antora.yml

Every attribute here depends on a successful GitHub lookup at build time. If a lookup fails, for example because of a rate limit or a missing token, the attribute is never set and any page that references it renders the attribute name in braces.

To keep a page buildable, seed a soft default in the consuming component's `antora.yml`. The trailing `@` makes it a fallback that the extension overwrites when the fetch succeeds:

[,yaml]
----
asciidoc:
  attributes:
    latest-redpanda-version: 26.2.1@
    latest-redpanda-version-short: 26.2@
----

CAUTION: Do not seed `full-version` with a value higher than the current release. `full-version` is the one attribute the extension refuses to move backwards, so a pin that is ahead of the current release stays ahead.

=== Environment variables

- `REDPANDA_GITHUB_TOKEN` (optional): A Personal access token (PAT) that has `repo` permissions for the `redpanda-data` GitHub organization.

NOTE: If you don't set the environment variable, the latest versions may not be fetched. When the environment variable is not set, the extension sends unauthenticated requests to GitHub. Unauthenticated requests may result in hitting the API rate limit and cause GitHub to reject the request.

=== Registration

```yaml
antora:
  extensions:
  - '@redpanda-data/docs-extensions-and-macros/extensions/version-fetcher/set-latest-version'
```

== Set available attachment versions

This extension scans the content catalog for generated JSON attachments and sets attributes that point UI templates at the newest file that actually exists, instead of the newest released version. Release-tracking attributes such as `latest-redpanda-tag` and `latest-connect-version` can be ahead of the newest generated JSON in the catalog; without this extension, the docs-ui `head-meta` partial falls back to a constructed production URL that returns 404 on every page view.

It sets the following attributes on component versions (never overwriting a value that is already set, so they can be pinned in `antora.yml`):

* `available-properties-tag`: newest `redpanda-properties-<tag>.json` attachment in the `reference` module of each version of the streaming component (`streaming`, or `ROOT` on older branches).
* `available-connect-version`: newest `connect-<version>.json` attachment in the `components` module of the connect component (`connect`, or `redpanda-connect` on older branches).
* `page-disable-property-tooltips`: set to `true` on streaming versions that have no properties JSON at all, so browsers never request a URL that cannot exist.

=== Environment variables

This extension does not require any environment variables.

=== Configuration options

There are no configurable options for this extension.

=== Registration

Register the `set-available-attachment-versions` extension in the Antora playbook under the `antora.extensions` key like so:

[source,yaml]
----
antora:
  extensions:
    - require: '@redpanda-data/docs-extensions-and-macros/extensions/set-available-attachment-versions'
----

== URL to xref

This extension converts absolute docs.redpanda.com URLs found in page and partial content into Antora xrefs, using the content catalog as the single source of truth. A URL is converted only when it maps to a page that is actually published in the current build, so the extension never guesses at URL structure. Converted links are validated by Antora's own xref resolution, and internal URLs that match no published page are logged as warnings — which makes this extension a broken-internal-link detector for the whole site.

Behavior details:

* Runs at `contentClassified`, before AsciiDoc conversion, so emitted xrefs flow through Antora's normal resolution and broken-xref logging.
* URLs inside listing, literal, fenced, and passthrough blocks, inline code spans, attribute entry lines, and macro attribute values (such as `link=` on an image macro) are left untouched.
* Legacy URL shapes (`/docs/...`, `/current/...`, `/vX.Y/...`, and pre-rename component slugs such as `/redpanda-connect/`) are rewritten to candidate paths, but a candidate is only used when it matches a published page.
* Fragments (`#anchor`) and link labels are preserved, including a label that a generator wrapped across a line break, whose line breaks are collapsed to single spaces.
* An unlabeled URL becomes `xref:...[]` so that Antora fills in the target page title. An unlabeled URL that carries a fragment is given link text explicitly, because Antora cannot resolve a section title and would render the raw resource ID as the link text: the extension uses the heading the fragment points at, falls back to the target page title, and leaves the URL as a raw link if it can read neither. Heading ids are also read from the partials a target page includes, because the reference pages that hold most anchor targets are thin wrappers around generated partials.
* Targets in the latest version of a component emit an unversioned xref; targets pinned to an older version emit `version@component:module:page`.
* A URL that points at a page's former path resolves through the `page-aliases` attribute that the page declares. Antora does not register those aliases as catalog files until it converts documents, which is after this extension runs, so the extension reads them from the page header. Only aliases in the same component and version as the page that declares them are mapped.
* A URL that carries a query string is left as a raw link, because an xref cannot express one and dropping it would change the link (for example `?platform=kubernetes`, which the UI reads to preselect a tab). These are reported at info level, not as warnings.
* Builds that publish the latest version under its real version number instead of a symbolic segment (such as this repository's preview build) still resolve `/current/...` URLs, so the same content works in both.

=== Environment variables

This extension does not require any environment variables.

=== Configuration options

hostnames (optional)::
List of hostnames treated as internal documentation URLs. Default: `['docs.redpanda.com']`.

ignore (optional)::
List of regular expressions matched against URL paths. Matching URLs are left untouched with no warning. Use this for paths on the docs domain that live outside the Antora catalog. Default: `['^/api/', '^/mcp(/|$)']` (the API reference is hosted by Bump.sh, and `/mcp` is the docs MCP server endpoint).

log_unconverted (optional)::
Whether to log a warning for each internal URL that matches no published page. Default: `true`.

=== Registration

Register the `url-to-xref` extension in the Antora playbook under the `antora.extensions` key like so:

[source,yaml]
----
antora:
  extensions:
    - require: '@redpanda-data/docs-extensions-and-macros/extensions/url-to-xref'
----

== External link checker

This extension collects every external http(s) URL referenced in page and partial content and verifies that it responds, reporting dead links in the build log. Internal links are covered by the url-to-xref extension plus Antora's own xref validation; this extension covers everything that points off-site.

Because it performs network requests, register it only in builds where that belongs (for example a scheduled nightly build), not necessarily on every preview build.

Responses are classified as follows:

* 2xx/3xx: ok
* 404/410: broken — logged as a warning, or at error level with `fail_on_broken`
* 401/403/429: unverifiable — logged at info level, because bot-walled or rate-limited sites are not broken
* Other statuses, network errors, and timeouts (after one retry): unverifiable — logged as a warning

=== What is not checked

The extension runs at `contentClassified`, on raw AsciiDoc, before Asciidoctor converts anything. Three kinds of URL are therefore left alone, because checking them reports a broken link where the published page has no link at all:

Code blocks::
URLs inside a listing (`----`), literal (`....`), passthrough (`++++`) or fenced (`+```+`) block. A fenced block counts as one even when the opening delimiter carries a language info string, such as `+```bash+` or `+```yml+`.

Comments::
URLs on a line comment (`//`) or inside a comment block (`////`). Asciidoctor drops these before rendering, so a generator's provenance note, a Doc Detective test step, or a writer's editorial aside never becomes a link.

Unresolved attribute references::
A URL still holding a literal `{name}` reference, such as `+https://github.com/{project-github}/issues+`. Attributes are substituted after this hook runs, so the real target is unknown here while the published URL is usually fine. These are logged at info level with the pages that reference them, and counted separately, so a genuinely undefined attribute is still visible.

=== Report attribution

Each finding names the repository, branch, and path the URL was found in, for example:

----
Broken external link https://example.com/gone (HTTP 404) referenced in: redpanda-data/docs@main:modules/manage/pages/x.adoc
----

An aggregated site builds the same Antora-relative path from several repositories and many version branches, so a path on its own does not identify a file well enough to act on.

=== Environment variables

LINK_CHECK::
Set to `true` to check links. Without it the extension registers and does nothing, so it can live in a playbook that preview builds also use without those builds making network requests.
+
This is an environment variable rather than a configuration option for two reasons: Antora does not interpolate environment variables into playbook values, and Antora consumes a playbook entry's own `enabled` key itself, before the config reaches the extension, so that name is not available.

=== Configuration options

internal_hostnames (optional)::
Hostnames to skip because they are internal documentation URLs. Default: `['docs.redpanda.com']`.

include (optional)::
List of regular expressions. When set, only URLs matching at least one pattern are checked.

exclude (optional)::
List of regular expressions. URLs matching any pattern are skipped.

versions (optional)::
Which component versions to check. `latest` checks only each component's latest version, plus every unversioned component; `all` checks every version in the build. Default: `latest`.
+
A site that publishes many versions of a component republishes the same dead link once per branch, and those older branches are frozen content that nobody edits, so checking them fills the report with findings that cannot be acted on.

concurrency (optional)::
Number of simultaneous requests. Default: `10`.

timeout (optional)::
Per-request timeout in milliseconds. Default: `10000`.

fail_on_broken (optional)::
Log broken links at error level so a build run with `--log-failure-level=error` fails. Default: `false`.

report_file (optional)::
Path to write a machine-readable JSON report to. Unset by default, in which case no report is written. Written every time the checker runs, including when there is nothing to say, so a consumer polling for this file can tell a clean run apart from one where the checker never ran at all. The report holds `counts`, a `results` array sorted broken-first, and `unresolvedAttributeReferences`; each result carries the URL, its classification and status, and a `refs` array of `{repo, refname, component, version, path}`. Intended for automation that has to act on the findings rather than read them.

=== Registration

Register the `external-link-checker` extension in the Antora playbook under the `antora.extensions` key like so:

== Solutions catalog

The `solutions-catalog` extension turns the `solutions` Antora component (one module per solution, no `nav.adoc`) into a validated catalog. It derives every `page-solution-*` attribute from the overview page's authored metadata, enforces the metadata contract at build time, computes the content graph between Product Docs pages and solutions, and publishes the catalog as site assets and as a component attribute the UI can render without file I/O.

When the build has no `solutions` component, every hook is a no-op, so the extension can be registered in a playbook before the content source exists.

Everything Antora-independent lives in pure modules next to `index.js`:

* `collect.js` reads the component into records (module = solution id) and derives repo, tag, asset, and attachments.
* `validate.js` holds every rule and returns `{ errors, warnings }`; errors are collected across all solutions and thrown once.
* `relationships.js` parses and validates `relationships.yml` and computes the scored graph.
* `outputs.js` shapes `page-solution`, `solutions.json`, and `solutions-graph.json`.

=== Hooks

contentClassified::
Structural fatals: the landing page `ROOT/pages/index.adoc` exists; every solution module has `pages/index.adoc`; module names are unique, lower-case slugs, and not reserved (`progress`, `download`, `api`, `index`, `examples`); `ROOT/partials/relationships.yml` parses as YAML and validates against `docs-data/solutions-relationships.schema.json`. A missing `relationships.yml` warns and builds with no editorial edges.

documentsConverted::
Register directly before `validate-attributes`, and after `unpublish-pages` and `add-git-dates`. Collects records, normalizes `page-categories` (parents added, unknown values fatal), runs every validation rule, applies `page-solution-status`, computes `page-related-solutions` for eligible Product Docs pages, writes the derived attributes onto solution pages, and sets the `solutions-catalog` component attribute on every component version. The attribute is set here rather than at `beforePublish` because Antora composes pages before `beforePublish` fires.

beforePublish::
Adds `assets/data/solutions.json` and `assets/data/solutions-graph.json` to the site. With `network_checks` on, verifies through the GitHub API that the release `<slug>/<version>` carries the asset `<slug>-<version>.zip` and warns if not (informational: the release workflow creates both after the merge that changes the version).

=== Environment variables

SOLUTIONS_INCLUDE_DRAFTS::
`true` builds solutions whose status is `draft` (previews and local builds). Overridden by the `include_drafts` config key when that is set.

CI::
With `network_checks: auto`, the release check runs only when `CI` is set and a GitHub token is available (`REDPANDA_GITHUB_TOKEN`, `GITHUB_TOKEN`, `GH_TOKEN`, or `GIT_CREDENTIALS`, see `cli-utils/github-token.js`).

=== Configuration options

max_related (optional)::
Maximum number of solutions shown on one Product Docs page. Default `3`.

min_score (optional)::
Minimum score an edge needs to be shown. Default `0.6`, which a category-only edge reaches with two shared leaf categories (`0.3 + 0.3`); one leaf plus the parent bonus scores `0.4` and stays hidden. Explicit and approved edges score `1.0` and `0.9` or more, so they always clear it.

network_checks (optional)::
`auto` (default), `true`, or `false`. See the `beforePublish` hook.

include_drafts (optional)::
`true` or `false`. When set, wins over `SOLUTIONS_INCLUDE_DRAFTS`. Default: follow the environment variable, else `false`.

public_repo (optional)::
`true` or `false`. Default `false`. The solutions repository is private, so by default no output names it: the public record has no `repo`, pages get no `page-solution-repo`, and the `.md` block carries neither `repository.url` nor `repository.ref`. Readers get the code through the download endpoint and the public attachments. Set `true` only if the repository becomes public. The release check reads the repository from the content source either way.

=== Component layout

[source]
----
docs/antora.yml                              name: solutions, version: ~, start_page: index.adoc
docs/modules/ROOT/pages/index.adoc           :page-layout: solutions-home
docs/modules/ROOT/partials/relationships.yml editorial edges (schema below)
docs/modules/<slug>/pages/index.adoc         overview, :page-layout: solution
docs/modules/<slug>/pages/<step-id>.adoc     one page per step, :page-layout: solution-step
docs/modules/<slug>/attachments/*            build-along files, published at /solutions/<slug>/_attachments/
docs/modules/<slug>/examples/*               code pulled into pages with the example$ include macro
docs/modules/examples/attachments/*          public tutorial code for Product Docs pages (not a solution)
----

Two modules are not solutions and are skipped by every rule, output, and the graph: `ROOT` (landing page and `relationships.yml`) and `examples` (public tutorial code that Product Docs pages link to as attachments). Neither needs a `pages/index.adoc`. `examples` is also a reserved id, so no solution can take that slug.

The module name is the solution id, the URL segment, the release tag prefix, and the asset prefix. Steps have no order of their own: `page-solution-steps` on the overview is the only ordering, and the set of listed ids must equal the set of non-index pages in the module.

=== Derived attributes

Written on the overview and every step page (complex values are JSON strings, read them with the UI's `parse-json` helper):

[cols="2,3"]
|===
| Attribute | Value

| `page-solution`
| The full record: `id`, `title`, `description`, `url`, `version`, `tag`, `asset`, `repo` (only with `public_repo: true`), `status`, `draft` (true only for a draft built with `include_drafts`), `featured`, `difficulty`, `duration`, `download`, `platforms`, `technologies`, `categories`, `useCases`, `files` (see <<Snippet provenance and the download allowlist>>), `personas`, `steps[{id, title, url, order, duration}]`, `relatedDocs[{id, title, url, provenance}]`, `relatedSolutions[{id, title, url}]`, `attachments[{name, url}]`, `supersededBy`, `lastModified`, and `verified{suite, specs, steps, commands, checks, media, verifyScript, redpandaVersion, runAt}` when the solution ships a verification manifest (see <<Verification>>). | `page-solution-step-count`
| Number of steps.

| `page-solution-step-index`
| `0` on the overview, `1..n` on steps.

| `page-solution-step-id`

| `page-solution-prev-url`, `page-solution-prev-title`, `page-solution-next-url`, `page-solution-next-title`

Derived, never authored: `page-solution-id` is the module name; `page-solution-repo` is `owner/name` from the page's git origin URL (https, ssh, and scp forms; a local `file://` origin yields an empty string); `page-solution-tag` is `<id>/<version>`; `page-solution-asset` is `<id>-<version>.zip`.

Eligible Product Docs pages receive `page-related-solutions`, only when non-empty: `[{id, title, url, description, difficulty, duration, technologies, provenance, score, reason}]` in rank order. Labs are excluded because they are the content solutions replace; section index pages because they carry an area's broad categories and would match every solution in that area.

=== Snippet provenance and the download allowlist

Every code block on a solution page is single-sourced from the solution's own code with `include::example$<path>`, so a reader can be offered the file behind the snippet. Two outputs carry that:

* Each listing block rendered from an `example$` include gets `data-solution-file="<path>"` in the HTML, plus `data-solution-tag="<tag>"` when the include selected exactly one tagged region, and the `sol-snippet` role. A hand-written listing gets none of these. This is the `add-solution-file-provenance` AsciiDoc extension (see <<Solution snippet provenance>>), which must be registered in `asciidoc.extensions`.
* The record's `files` is the deduplicated, sorted set of those paths across the solution's overview and step pages: exactly the set a reader may download and nothing more. The download endpoint rejects any path that is not in it.

`files` is read back out of the rendered HTML rather than by re-reading the AsciiDoc, which is what keeps the two in step: a snippet a reader can see is in the list, and a path no page renders cannot be. A solution whose pages render no includes has an empty list.

Provenance depends on Antora attaching block source locations, which it does only when `asciidoc.sourcemap` is set. The `solutions-catalog` extension sets it at `beforeProcess` so no playbook has to remember; without it the attributes and the allowlist would both be silently empty.

=== Verification

A solution's Doc Detective evidence comes from `verification.json`, an attachment of the solution's module that the monorepo's runner writes after a passing full run, from that run's own results, and commits like the captured media:

[,json]
----
{"suite":"doc-detective","specs":11,"steps":50,"commands":34,"checks":23,"media":2,
 "verify_script":"PASS (9/9)","redpanda_version":"v26.2.2","run_at":"2026-09-14T09:12:00Z"}
----

The file is read from the content catalog, mapped onto the record's `verified` (the manifest's `verify_script`, `redpanda_version`, and `run_at` become `verifyScript`, `redpandaVersion`, and `runAt`), and mirrored as `page-solution-verified-at` and `page-solution-verified-version` so a step page template can show when the solution was last verified without parsing JSON. Because it is machine evidence rather than build-along scaffolding, it is left out of the record's `attachments` list.

Nothing about verification is inferred. A solution with no manifest has no `verified` key, and the build warns when that solution is published, which is the build-side twin of the monorepo's `check-metadata`. A manifest that does not parse, is not a JSON object, or carries none of the known fields produces no key either, plus a warning naming the file and the reason. `run_at` is never synthesised from a git date: when it is missing or not an ISO 8601 timestamp the build warns and the value is published exactly as the manifest wrote it, so the disagreement is visible rather than papered over.

=== Status

draft::
Unpublished unless `include_drafts` or `SOLUTIONS_INCLUDE_DRAFTS=true`: `out` is deleted on the module's pages, aliases, attachments, and images, and the page and alias URLs are added to `siteCatalog.unpublishedPages` (re-asserted at `navigationBuilt` and `beforePublish`, so the list survives `unpublish-pages` resetting it if that runs later). When drafts are included (previews, local builds) they behave as published for every output: they are in `solutions.json`, the `solutions-catalog` attribute, the graph, `page-related-solutions`, and the nav, so the preview shows the real landing page and recommendations. The record keeps `status: "draft"` and adds `draft: true`, which is what the UI's status chip reads. The build still warns that drafts are being built, and the release check skips them. Never in the catalog or the graph when unpublished; when built, it is in the graph with `shown: false` and the build warns that drafts are being built. Section checks are skipped for drafts.

published::
Everything applies.

deprecated::
Publishes, appears in the catalog with `supersededBy`, and is excluded from recommendations and from the featured check.

=== Scoring

Every (doc, solution) pair with any signal becomes an edge with provenance:

[cols="1,2,1"]
|===
| Provenance | Signal | Score

| `explicit`
| The doc is listed in the solution's `page-solution-related-docs`.
| `1.0`

| `editor-approved`
| `relationships.yml` entry with `status: approved`.
| `max(0.9, confidence)`

| `rejected`
| `relationships.yml` entry with `status: rejected`. Beats every other signal, including an authored `page-solution-related-docs` entry: the doc gets no recommendation and the overview's `relatedDocs` drops it, with a build warning naming the pair so the disagreement is resolved in one place.
| kept in the graph, `shown: false`

| `category`
| Shared categories after normalization.
| `0.3` per shared *leaf* category + `0.1` per shared *parent* category (parents capped at `0.1` per edge in total), capped at `0.85`
|===

A category is a leaf when it is a subcategory, or a top-level category that has no subcategories of its own: `Schema Registry`, `Troubleshooting`, `Redpanda Console`, `rpk`, `Streaming`, `Emergency Response`, and `Agentic Data Plane` are all leaves, and are as specific a statement about a page as any subcategory. A category is a parent only when it has subcategories, which makes it broad by construction: `normalizeCategories` adds it automatically to every page that names one of its children, so a shared parent says "same product area" and nothing more. That distinction is why the two scores exist, and why it is the shape of the taxonomy rather than the indent level that decides: scoring every top-level category at `0.1` meant a solution teaching Schema Registry could not reach the Schema Registry pages by category at all, only through an explicit link.

Why the threshold sits at two leaves: an audit of the demo build's edges found that pages sharing one broad subcategory such as `Clients` with a solution were not relevant to it, while pages sharing two or more were. One leaf is too weak a signal in practice, and a parent bonus can never carry an edge over the line on its own. Where a single page is genuinely the right companion, `page-solution-related-docs` (explicit, `1.0`) is the tool; `relationships.yml` (`approved`) covers the cases an editor confirms after the fact.

`pending` entries are ignored (they are Stage 2 ML output awaiting review); the build logs how many there are. The platform filter applies to category edges only: a Cloud doc (`page-cloud` or `env-cloud`) needs `cloud` in the solution's platforms; a Kubernetes, Linux, or Docker doc needs `self-managed`; a doc with no marker matches everything. Edges below `min_score`, edges to non-published solutions, and edges past `max_related` stay in the graph with `shown: false` and a reason. Ranking is score descending, then featured first, then `lastModified` descending (from `add-git-dates`), then title ascending, so the output is the same on every build.

=== Outputs

`assets/data/solutions.json`::
`{ generatedAt, siteUrl, solutions[], facets: { industries, useCases, categories, technologies, difficulty, platforms } }`. `solutions` holds the public record of every published and deprecated solution, sorted by id. Each facet is `[{ value, count }]` sorted by value, and a value carried by every solution is dropped because it narrows nothing. The `categories` facet counts the categories each solution's author wrote that are leaves of the taxonomy (a subcategory, or a top-level category with no subcategories). Parent categories are left out of the facet, including the ones the build adds, though they stay in each record's `categories`. The same JSON is set as the `solutions-catalog` attribute on every component version. In Handlebars the precise path is `page.componentVersion.asciidoc.attributes['solutions-catalog']` (the version the page belongs to). docs-ui's `get-index-data.js` reads `page.component.asciidoc.attributes[...]` instead; that also works because Antora's component object exposes `asciidoc` as a getter onto `component.latest.asciidoc`, and the attribute is set on every version including the latest. Either path returns the same string; `componentVersion` is the one to prefer in new helpers because it does not depend on which version is latest.

`assets/data/solutions-graph.json`::
`{ generatedAt, siteUrl, settings: { maxRelated, minScore }, edges: [{ doc, docUrl, solution, provenance, score, shown, rank, reason }], coverage }`. Every recommendation a reader sees is explained here, and so is every one they do not. `coverage` is the category coverage report: `{ solutions: { <slug>: { categories: { <category>: { pages, level: 'sub'|'top' } }, zeroMatch: [...] } }, uncategorizedEligiblePages, uncategorizedSample: [first 20 URLs] }`, where `pages` counts eligible doc pages (the same set recommendations use) that carry the category after normalization, and `zeroMatch` lists the solution's categories no doc page shares.

=== Coverage report

Once per build, after recommendations are computed, the extension logs one info line per published (or included draft) solution and one summary line:

[source]
----
solutions-catalog: multiplayer-gaming reach: Stream Processing=19 (sub), Clients=13 (sub), Development=28 (top); zero-match: none
solutions-catalog: 47 doc pages decorated, 312 eligible doc pages without categories
----

A category in `zero-match` reaches nobody: either the Product Docs pages that should carry it are missing `page-categories`, or the solution is categorized wrongly. The summary's second number is the size of the opportunity: eligible doc pages that can never receive a category recommendation until they are categorized. The same data is in `solutions-graph.json` under `coverage`.

=== relationships.yml

Lives in the solutions repo at `docs/modules/ROOT/partials/relationships.yml` and is read through the content catalog, so the ML bot and editors PR into one file that is versioned with the content. Shape (schema: `docs-data/solutions-relationships.schema.json`, exported as `@redpanda-data/docs-extensions-and-macros/docs-data/solutions-relationships.schema.json`):

[source,yaml]
----
version: 1
relationships:
  - solution: multiplayer-gaming                       # module name, lower-case slug
    doc: streaming:develop:consume-data/consumer-offsets.adoc   # fully qualified page ID
    status: approved                                   # approved | rejected | pending
    source: editor                                     # ml | editor (optional)
    confidence: 0.95                                   # 0..1 (optional)
    reason: Consumer groups are the worked example.    # optional, max 500 chars
    reviewedBy: jake                                   # optional
    reviewedAt: 2026-09-12                             # optional, YYYY-MM-DD
----

Unknown keys, a bad `status`, a `solution` that is not a slug, or a `doc` that is not fully qualified fail the schema and the build. The same pair listed twice is fatal. A `solution` or `doc` that does not exist in the build only warns ("orphaned") and the entry is dropped, so the file can reference pages that live in a content source the current build does not include. YAML is loaded with the core schema, so an unquoted date stays a string.

=== Warnings

Missing `page-solution-related-docs`; a published solution with no `verification.json`; an unreadable `verification.json`; a `run_at` that is absent or not an ISO 8601 timestamp; a description over 200 characters; no published solution featured; orphaned relationships; pending relationships (count); drafts being built; `page-valid-categories` unavailable (category validation and category edges are skipped); a release or asset missing on GitHub when `network_checks` runs.

== Solution snippet provenance

The `add-solution-file-provenance` AsciiDoc extension stamps each code block on a solution page with the example file it was included from, so the UI can offer the reader that file. It is an Asciidoctor extension, not an Antora one, so it belongs in `asciidoc.extensions`:

[,yaml]
----
asciidoc:
  extensions:
  - '@redpanda-data/docs-extensions-and-macros/asciidoc-extensions/add-solution-file-provenance'
----

A listing block rendered from `include::example$<path>` gets:

`data-solution-file`:: The path of the included file, relative to the module's `examples` directory (for example `services/leaderboard/main.go`).
`data-solution-tag`:: The tag the include selected, when it selected exactly one (`tags=handler` or `tag=handler`). A whole-file include, several regions (`tags=a;b`), a negation, or a wildcard leaves this off rather than naming something the reader is not looking at.
`sol-snippet`:: A role, so the UI can find these blocks. Roles already on the block are kept.

A hand-written listing gets none of them, and pages outside the `solutions` component are left alone entirely.

How it works, in case it ever needs changing: Antora's include processor pushes the resolved file onto the reader carrying its Antora source record and a parent cursor that points at the include directive's own line, so a tree processor reading a block's `source_location` can tell which example file the block came from and which line of the page included it. The tag is read from that directive line, because Asciidoctor keeps the included lines and not the selection that produced them. Asciidoctor's HTML converter emits no `data-*` attributes on a listing block, so the tree processor marks each block with a per-document role token and a postprocessor swaps that token for the attributes; the token is unique per block, so nothing depends on blocks and HTML being in the same order.

IMPORTANT: Block source locations exist only when `asciidoc.sourcemap` is set. The `solutions-catalog` extension sets it at `beforeProcess`, so registering that extension is enough; with neither, this extension emits nothing. The catalog turns these attributes into the solution record's `files` allowlist (see <<Snippet provenance and the download allowlist>>).

== Shared helpers

Two modules under `extension-utils/` replace copies that had drifted apart across four extensions. Both are exported and have no Antora dependency.

`extension-utils/deployment-type`::
`getDeploymentType(attributes)` returns `Kubernetes`, `Linux`, `Docker`, `Redpanda Cloud`, or `''`, checking `env-kubernetes`, `env-linux`, `env-docker`, then `env-cloud` or `page-cloud`, in that order. Used by `generate-index-data`, the Algolia indexer, `find-related-docs`, `find-related-labs`, and `solutions-catalog`.

`extension-utils/categories`::
`createCategoryMap(validCategories)` builds `{ categories: Set, subcategories: Set, parentMap: Map, withChildren: Set }` from the `page-valid-categories` list, where `withChildren` holds the top-level categories that actually have subcategories. `isLeafCategory(category, map)` reports whether a category is as specific as it gets (a subcategory, or a top-level category with no children), which is what the solutions scorer weighs. `parseCategoryList(value)` splits a comma list. `normalizeCategories(list, map)` returns `{ categories, invalid, parentsAdded }`: authored order kept, parents appended, unknown values removed. `validate-attributes` logs the `invalid` and `parentsAdded` results; `solutions-catalog` treats `invalid` as fatal. Adding a category or subcategory to `valid-categories.yml` needs no code change here.

== Replace attributes in attachments

This extension automates the replacement of AsciiDoc attribute placeholders with their respective values within attachment files, such as CSS, HTML, and YAML.

[NOTE]
====
- The `@` character is removed from attribute values to prevent potential issues with CSS or HTML syntax.
- If the same attribute placeholder is used multiple times within a file, all instances will be replaced with the attribute's value.
====

=== Environment variables

This extension does not require any environment variables.

=== Configuration options

The extension accepts the following configuration options in the Antora playbook:

data.replacements (required):: An array of replacement configurations. Each configuration can target multiple components and define specific file patterns and custom replacement rules.

* `components` (array of strings, required): Lists the names of the Antora components whose attachments should undergo attribute replacement.

* `file_patterns` (array of strings, required): Glob patterns specifying which attachment files to process. These patterns determine the files that will undergo attribute replacement based on their paths within the content catalog.

* `custom_replacements` (array of objects, optional): Defines custom search-and-replace rules to be applied to the matched files. Each rule consists of:

              - 'API'

== Git full clone

This extension ensures Antora uses full git clones instead of shallow clones for remote repositories. Full git history is required for accurate git date extraction by the `add-git-dates` extension.

The extension uses a two-phase approach:

1. **Phase 1**: Sets `git.depth = 0` in playbook during registration (best effort)
2. **Phase 2**: After content aggregation, detects repos with a `shallow` file and runs `git fetch --unshallow` to convert them to full clones

This two-phase approach works around Antora's default shallow clone behavior, which can't always be overridden via playbook configuration alone.

=== How it works

. During extension registration, modifies playbook to request `depth=0` for all remote repos
. After Antora aggregates content, checks each repo's git directory for a `shallow` file
. For any shallow repos found, runs `git fetch --unshallow` with timeout protection
. On subsequent builds with warm cache, repos are already full clones (no unshallow needed)

=== Performance

**First build** (cold cache):

- Unshallow: ~1-5 seconds per remote repo
- Total overhead: ~5-20 seconds depending on repo count

**Subsequent builds** (warm cache):

- Unshallow: 0 seconds (repos already full clones)
- Total overhead: minimal

**Scalability:**

- 1k commits: ~1-2s unshallow time
- 5k commits: ~3-5s unshallow time
- 10k commits: ~5-10s unshallow time
- 50k+ commits: Consider increasing timeout or pre-populating cache

=== Environment variables

This extension does not require any environment variables.

=== Configuration options

The extension accepts the following configuration options:

skipUnshallow (optional, default: false):: Set to `true` to skip the unshallow phase entirely. Useful for air-gapped CI/CD environments or when git dates are not needed.

unshallowTimeout (optional, default: 60000):: Timeout in milliseconds for the unshallow operation per repository. Increase this for very large repositories (50k+ commits).

=== Registration

Basic configuration (recommended):

[,yaml]
----
antora:
  extensions:
  - require: '@redpanda-data/docs-extensions-and-macros/extensions/git-full-clone'
----

With custom timeout for large repos:

[,yaml]
----
antora:
  extensions:
  - require: '@redpanda-data/docs-extensions-and-macros/extensions/git-full-clone'
    unshallowTimeout: 120000  # 2 minutes for very large repos
----

For air-gapped environments:

[,yaml]
----
antora:
  extensions:
  - require: '@redpanda-data/docs-extensions-and-macros/extensions/git-full-clone'
    skipUnshallow: true  # Skip network-dependent unshallow
----

=== Production considerations

**Netlify/CI builds:**

- First build or cache clear: Pays unshallow cost (~5-20s)
- Subsequent builds with warm cache: No unshallow needed
- Consider pre-populating Antora cache in CI for faster cold builds

**Timeout protection:**

- Default 60-second timeout prevents hanging on slow networks
- Graceful failure: Build continues even if unshallow times out
- Git dates may be incomplete for timed-out repos (warning logged)

**Error handling:**

- Network failures don't break the build
- Timeout failures are logged with guidance to increase timeout
- Falls back to available git history if unshallow fails

**Optimization for very large repos (50k+ commits):**

1. Increase `unshallowTimeout` to 120000ms or higher
2. Pre-populate Antora cache with full clones in CI/CD
3. Use persistent cache in Netlify to avoid repeated unshallows
4. Consider implementing Neon KV caching for git dates (future optimization)

== Add Git dates

This extension adds accurate git-based created and modified dates to documentation pages by analyzing commit history. It uses isomorphic-git (bundled with Antora) to walk the commit history of each repository and detects actual file modifications by comparing tree objects between commits.

The extension adds the following attributes to each page:

- `page-git-created-date`: The date when the file was first committed (YYYY-MM-DD format)
- `page-git-modified-date`: The date when the file was last modified (YYYY-MM-DD format)

These attributes are available for use in UI templates (for metadata, display banners, etc.) and are exported to markdown files for AI consumption.

=== How it works

. Groups pages by repository AND branch (same repo can have multiple branches: v/23.3, v/24.1, main)
. Walks git log once per repo+branch using isomorphic-git
. Compares tree objects between commits to detect actual file modifications (not just file existence)
. Builds a filepath → {created, modified} map for each repo+branch
. Applies dates to pages based on their source file path

This approach is **O(commits)** instead of **O(files × commits)**, making it efficient for large repositories.

=== Performance

- **Full clone** (depth=0): ~15s for 4128 pages across 12 branches (14.5s git processing)
- **Per-page overhead**: ~3-5ms per page

=== Environment variables

This extension does not require any environment variables.

=== Configuration options

This extension does not require configuration options. However, it works best with **full git clones** rather than shallow clones.

To enable full clones for remote repositories, use the `git-full-clone` extension:

```yaml

  extensions:
  - require: '@redpanda-data/docs-extensions-and-macros/extensions/git-full-clone'
  - require: '@redpanda-data/docs-extensions-and-macros/extensions/add-git-dates'
```

=== Registration

```yaml

  extensions:
  - require: '@redpanda-data/docs-extensions-and-macros/extensions/add-git-dates'
```

=== UI integration

=== Solution metadata

Pages of the `solutions` component carry their metadata into the `.md` twin as one structured `solution:` block, because the consumer is a machine: agents and LLMs read the Markdown, not the rendered page. Every value is projected from the `page-solution` record that <<Solutions catalog>> builds, so the facts have a single source. The raw JSON attributes (`page-solution`, `page-solution-nav`, `page-related-solutions`) stay blocked from the frontmatter. This is a shaped projection, not a dump.

On a solution overview:

[,yaml]
----
solution:
  id: multiplayer-gaming
  version: v1.0.0
  status: draft
  difficulty: intermediate
  duration_minutes: 45
  technologies:
    - Redpanda
    - Schema Registry
    - Go
  platforms:
    - self-managed
    - cloud
  categories:
    - Topics and Partitions
    - Producers
  use_cases:
    - Real-time analytics
    - Event-driven microservices
  industries:
    - Gaming
  steps:
    - id: start-environment
      title: Start the environment
      url: /solutions/multiplayer-gaming/start-environment/
  related_docs:
    - title: Consumer offsets
      url: /streaming/develop/consumer-offsets/
  repository:
    url: https://github.com/redpanda-data/redpanda-solutions
    ref: multiplayer-gaming/v1.0.0
    download: authenticated
----

A step page gets the same block without `steps`, and with its own position instead: `step: {id, index, of}`. `files` lists the snippets the solution's pages render, which is the same allowlist the download endpoint enforces, so an agent reading the `.md` can fetch exactly that set; it is omitted when the solution renders none. `repository.ref` is the release tag that exists (`<id>/<version>`), not the bare version, so a consumer can check the ref out. `repository.url` and `repository.ref` appear only when the catalog publishes the repository (`public_repo: true`); for the default private repository the block carries only `repository.download`, and `files` names what the download serves. The generic frontmatter (title, description, and the allowlist) is unchanged, and `personas` stays a top-level key rather than moving into the block.

A field whose value cannot be sourced truthfully is left out rather than guessed, and so is an empty list, so that every key present is a claim. `verified` follows from the solution's `verification.json` manifest (see <<Verification>>) and is emitted with that file's own snake_case keys, so the block and the file read the same way:

[,yaml]
----
solution:
  verified:
    suite: doc-detective
    specs: 11
    steps: 50
    commands: 34
    checks: 23
    media: 2
    verify_script: PASS (9/9)
    redpanda_version: v26.2.2
    run_at: '2026-09-14T09:12:00Z'
----

A solution with no manifest, or one whose manifest could not be read, has no `verified` key. Only the fields the manifest carried are emitted.

==== Field naming

The field names line up with the docmeta metadata vocabularies proposal (hawkeyexl/manni proposal 0023 and its nine vocabularies): `core` requires `title` and `description`; `audience` covers who the page serves, which is personas and `difficulty`; `lifecycle` covers `status` and `version`; `structure` covers what the page connects to, which is `steps` and `related_docs`; `evals` covers what must be true of the page, which is the generated Doc Detective specs. Nothing in that proposal is registered, so nothing here claims conformance. The shape is chosen so that adopting those vocabularies later is a change to this emitter alone.

Two of its principles this already follows:

One value is a string and many values are a list::
`id`, `status`, and `difficulty` are strings; `technologies` and `platforms` are lists even when they hold one entry.

Metadata claims content, not rendering::
This is why `page-layout` and featured placement stay out of the block. They say where a page appears, not what it is about.
