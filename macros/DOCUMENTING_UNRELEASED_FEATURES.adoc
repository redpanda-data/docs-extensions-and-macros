= Documenting properties and enterprise features before they ship
:toc:
:toclevels: 3

How to reference a configuration property or an enterprise feature that is not in a released version of Redpanda yet, so that the build checks your work instead of you having to remember which release something landed in.

For how the macros work generally, see link:PROPERTY_AND_ENTERPRISE_REFERENCES.adoc[the explainer] and link:REFERENCE.adoc[the macros reference].

== The two situations

Redpanda cuts release candidates before every release, and the docs track them on a prerelease branch (`beta`) that publishes under `/beta/` on the site. Two different things can be true of a feature or property on that branch:

*Unreleased.* It exists only in a release candidate. Nobody outside can get it yet. You are writing the docs ahead of the release so they ship with it.

*Released beta.* It is publicly available, but as a beta: real users can turn it on, and it may still change.

The distinction matters because it decides where a mention is allowed. An unreleased thing referenced from released docs promises readers something they cannot have. A released beta is fine to mention anywhere, as long as readers can see it is a beta.

The macros enforce that distinction, so the rule you need to remember is short: *write the mention on the branch the feature is actually on, and let the build tell you if you got it wrong.*

== Properties in a release candidate

=== What has to exist first

A property mention is only as good as the property data behind it. Each release series publishes its own `redpanda-properties-v<major>.<minor>.<patch>.json` as a reference-module attachment, and a page validates against the file for *its own* series. A prerelease branch is no exception: it needs a file generated from the RC tag.

[,bash]
----
# On the beta branch, from the docs repo
npx doc-tools generate property-docs --tag v26.3.1-rc1
----

`--tag` accepts release-candidate tags. The generated file is `redpanda-properties-v26.3.1-rc1.json`, and because its series is `26.3` it is picked up by a component version at `version: 26.3`.

Regenerate it for each RC. Tags compare by release precedence, so `rc2` supersedes `rc1` and the GA `v26.3.1` supersedes both -- you can leave older RC files in place and the build will use the newest.

=== Writing the mention

Once that file is committed on the branch, nothing special is needed. Write the macro as you would anywhere:

[,asciidoc]
----
Set prop:my_new_property[] to enable the thing.
----

The build validates the name against the RC data. A typo gets a warning naming the file it checked. A property that only exists in the RC validates on the beta branch and, correctly, fails validation if someone copies the sentence to a released branch, because it is not in that release's data.

=== If you forget the property data

You get told, once per component version, with the command to run:

[literal]
----
prop macro: streaming@26.3 publishes no redpanda-properties-v26.3.*.json attachment
in its reference module (found for other series: v26.2.1). prop: targets on 26.3
pages are therefore not validated and their tooltips carry no data, rather than
being checked against another release's properties. Generate it with
'npx doc-tools generate property-docs --tag v26.3.<patch>' on that branch, or
leave prop: out of 26.3 content.
----

Mentions render as plain code with no tooltip until the file exists. That is deliberate: validating 26.3 content against 26.2 data would accept properties that release never had and flag removed ones as typos.

=== Cloud pages and release candidates

Cloud runs released Redpanda, so Cloud pages always validate against the newest *GA* property data and ignore release candidates entirely. You cannot document an RC-only property on a Cloud page, and you should not want to -- the property is not in Cloud until the release ships and Cloud picks it up.

A property is available to Cloud only when its `cloud_supported` field is `true`, which comes from the Cloud support data the extractor fetches. For a property new in an RC that flag is `false`, so a Cloud mention renders as plain code with a warning. When Cloud gains the property, regenerating the data flips the flag and the mention starts working with no docs change.

== Enterprise features in a release candidate

Enterprise features are declared in the registry (`enterprise-features.yml` in the `shared` component), and the release status lives there rather than in each mention. That way one edit updates every reference and every generated licensing table.

=== Declaring the status

[,yaml]
----
# Only in a release candidate: not public yet.
- name: My Upcoming Feature
  scope: redpanda
  status: unreleased
  description: What it does.
  expiration: What happens when the licence expires.

# Publicly available as a beta.
- name: My Beta Feature
  scope: redpanda
  status: beta
  description: What it does.
  expiration: What happens when the licence expires.
----

`status` is one of:

[cols="1,3a"]
|===
| Value | Meaning

| `ga`
| Shipped. The default when `status` is absent, so existing entries need no change. Referenced anywhere, no badge.

| `beta`
| Publicly available as a beta. Referenced anywhere. Renders a `beta` badge in prose and in the licensing tables.

| `unreleased`
| In a release candidate only. Referenced *only* from prerelease docs. Renders an `unreleased` badge there, and is omitted from licensing tables on released docs.
|===

`beta: true` is the older spelling and still means `status: beta`. Prefer `status` in new entries: it can express "not public at all", which a boolean cannot.

Add `status-tooltip` to override the hover text on an `unreleased` badge, or `beta-tooltip` on a `beta` badge.

=== Writing the mention

Unchanged:

[,asciidoc]
----
enterprise:My Upcoming Feature[] requires a licence.
----

On the prerelease branch this renders with the `unreleased` badge. On released docs it renders as plain text with no enterprise styling, no tooltip, and no link, plus a warning:

[literal]
----
enterprise:My Upcoming Feature[] in modules/manage/pages/example.adoc:
'My Upcoming Feature' is marked status: unreleased in the enterprise features
registry, so it is only documented for an upcoming release. This page belongs to
a released version, so the mention renders as plain text with no enterprise
styling, tooltip, or link. Move the mention to the prerelease (beta) branch, or
change the status once the feature ships.
----

The `unreleased` badge cannot be suppressed with `enterprise-beta-badge=false`. "Not in a release yet" is information a reader needs, not decoration.

=== Licensing tables

`enterprise_features::<scope>[]` omits `unreleased` features on released docs, because the table states what a licence covers today and listing something unavailable makes it wrong. On prerelease docs the same table lists them with their badge.

== When the release ships

Two edits, in this order:

. *Properties.* Generate the GA property data on the branch that becomes the released version:
+
[,bash]
----
npx doc-tools generate property-docs --tag v26.3.1
----
+
The GA tag supersedes its release candidates automatically, so no mention changes. Cloud starts seeing the new properties when the Cloud support data marks them `cloud_supported`.

. *Enterprise features.* Change `status: unreleased` to `status: beta` (if it ships as a public beta) or remove the `status` field (if it ships generally). Every mention and every table updates from that one edit.

Nothing in prose needs touching for either.

== Checklist

Before opening a PR that documents something unreleased:

* [ ] The mention is on the prerelease branch, not on `main` or a released `v/*` branch.
* [ ] For a property: the RC property JSON is committed on that branch, generated from the RC tag.
* [ ] For an enterprise feature: the registry entry has `status: unreleased`, not `beta: true`, unless it is genuinely a public beta.
* [ ] The build log has no `prop macro:` or `enterprise:` warnings for your additions.
* [ ] No mention of an unreleased property or feature on a Cloud page.

== Why the build enforces this rather than trusting reviewers

Every one of these rules is checkable from data the build already has: which release series a page belongs to, whether its component version is a prerelease, which properties that release actually defines, and what the registry says about a feature's status. A reviewer would have to hold all of that in their head across hundreds of mentions and nine doc versions.

So the macros check it, and the failure mode is always the same: render the plain name and say why. That is deliberate. A wrong tooltip or a link to a page describing a feature nobody can get is worse than no tooltip at all, because the reader has no way to tell it is wrong.
