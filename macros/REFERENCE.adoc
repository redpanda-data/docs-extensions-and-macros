= AsciiDoc macros reference
:toc:
:toclevels: 3

Reference documentation for all AsciiDoc macros and extensions provided by this library.

IMPORTANT: Be sure to register each extension under the `asciidoc.extensions` key in the playbook, not the `antora.extensions` key.

== Add line numbers and highlights

This extension adds the necessary classes to make line numbers and line highlighting work with Prism.js.

=== Registration

```yaml
antora:
  extensions:
  - '@redpanda-data/docs-extensions-and-macros/asciidoc-extensions/add-line-numbers-highlights'
```

== config_ref

IMPORTANT: `config_ref` is deprecated. The <<prop>> macro supersedes all of its functionality: it validates names against the published property reference, discovers the target page dynamically instead of taking a manual path, powers hover tooltips, and its `helm-path=auto` attribute replaces `config_ref`'s Kubernetes prefixing with a per-property correct Helm values path (`config_ref` prefixed every property with `storage.tiered.config.`, mislabeling non-tiered properties). Migrate call sites with `doc-tools generate migrate-property-refs --config-refs`. The macro stays registered only because the generated property partials still emit it.

This inline macro is used to generate a reference to a configuration value in the Redpanda documentation. The macro's parameters allow for control over the generated reference's format and the type of output produced.

=== Usage

The `config_ref` macro is used in an AsciiDoc document as follows:

[,asciidoc]
----
config_ref:configRef,isLink,path[]
----

The `config_ref` macro takes three parameters:

configRef::
This is the configuration reference, which is also used to generate the anchor link if `isLink` is `true`.

isLink::
Whether the output should be a link. If `isLink` is set to `true`, the output will be a cross-reference (xref) to the relevant configuration value.

path::
This is the path to the document where the configuration value is defined. This parameter is used to to generate the link if `isLink` is `true`.

IMPORTANT: The path must be the name of a document at the root of the `reference` module.

NOTE: The `config_ref` macro is environment-aware. It checks if the document it is being used in is part of a Kubernetes environment by checking if the `env-kubernetes` attribute is set in the document's attributes. Depending on this check, it either prepends `storage.tieredConfig.` to the `configRef` or just uses the `configRef` as is.

For example:

[,asciidoc]
----
config_ref:example_config,true,tunable-properties[]
----

=== Registration

[,yaml]
----
asciidoc:
  extensions:
    - '@redpanda-data/docs-extensions-and-macros/macros/config-ref'
----

== enterprise

This inline macro marks a feature as an enterprise feature in prose. The feature name renders as a uniquely styled term with a tooltip explaining that the feature requires an Enterprise Edition license, and links to the feature's documentation or to the licensing page.

The macro validates its target against the enterprise features registry: `modules/ROOT/partials/enterprise-features.yml` in the `shared` component (the `shared/` folder of the docs repository). The registry is the canonical list of enterprise features and their approved external names. Targets are matched case-insensitively, including aliases, and the canonical name, feature page link, and tooltip come from the matching entry. A target that matches no entry is reported according to `enterprise-validate`. To mark a new feature as enterprise, add it to the registry first.

=== Usage

[,asciidoc]
----
enterprise:Continuous Data Balancing[]
enterprise:Tiered Storage[xref=manage:tiered-storage.adoc]
enterprise:Audit Logging[text=audit logging]
enterprise:Iceberg Topics[tooltip=Iceberg Topics requires an Enterprise Edition license and object storage.]
----

The macro target is the feature name, which can contain spaces. Named attributes:

xref::
Optional Antora resource ID of the feature's documentation page. Overrides the registry entry's link. When neither is set, the term links to the licensing page.
+
Registry entries can carry environment-specific pages: on pages with the `env-cloud` attribute the entry's `xref-cloud` is used, on pages with `env-kubernetes` the entry's `xref-kubernetes` is used, and otherwise the entry's default `xref` (the Linux or generic self-managed page). This mirrors the `config_ref` macro's environment awareness.

text::
Optional display text override. Use it when the sentence needs different casing or phrasing than the feature name.

tooltip::
Optional tooltip text override. Overrides the registry entry's `tooltip`. The default is `<feature> requires an Enterprise Edition license.`

=== Configuration options

enterprise-validate::
How to report a target that does not match any registry entry: `warn` (default) logs a build warning with the file path and close-match suggestions, `error` fails the build, and `off` disables validation. When no registry is available in the build, the macro renders without validation and logs a single warning.

enterprise-licensing-page::
Resource ID of the licensing page used when no `xref` attribute is given. The default is `get-started:licensing/overview.adoc`.

enterprise-feature-role::
CSS class applied to the wrapping span. The default is `enterprise-feature`. Style this class in the UI bundle to give enterprise terms a consistent visual treatment.

enterprise-tooltip::
Controls the tooltip attribute: `title` (default), `true` (renders `data-enterprise-tooltip` for UI-driven tooltips), any attribute name starting with `data-`, or `false` to disable tooltips.

enterprise-links::
Set to `false` to render the term without a link.

enterprise-beta-badge::
Set to `false` to suppress the beta badge in prose. Generated tables always show it. See <<beta-features>>.

[[beta-features]]
=== Beta features

Add `beta: true` to a registry entry to mark the feature as beta. The macro then renders a beta badge after the feature name, both in prose and in the generated `enterprise_features` tables, so one registry field keeps every reference consistent:

[,yaml]
----
- name: Stretch Clusters
  scope: operator
  beta: true
  feature-suffix: (StretchCluster resource)
----

Add `beta-tooltip` to give the badge hover text.

Do not write a `badge:` macro call into `feature-suffix` to achieve this. The badge is emitted as an inline passthrough, so it renders whether or not the consuming playbook registers the `badge` macro, and it degrades to the text `(beta)` in Markdown. A hand-written macro call renders as literal source text in any build that does not register that macro.

=== Markdown output

In HTML, the enterprise signal is carried by the span's CSS class and its tooltip attribute. Both are attributes, so an HTML-to-Markdown conversion drops them and the term arrives as an ordinary feature name. To keep the signal for readers of the Markdown pages, including AI agents, the `convert-to-markdown` extension appends an explicit `(enterprise)` marker and preserves any link:

[,markdown]
----
Enable [Tiered Storage](../manage/tiered-storage.md) (enterprise) today.
----

A feature that is also marked `beta: true` gets one combined marker rather than two adjacent parentheticals:

[,markdown]
----
Enable [Stretch Clusters](../deploy/stretch-clusters.md) (enterprise, beta) today.
----

This applies to the inline macro. The tables from `enterprise_features` need no enterprise marker, because their expiration column already states the licensing behavior as text. A beta badge in a table converts to `(beta)` on its own.

=== Registration

[,yaml]
----
asciidoc:
  extensions:
    - '@redpanda-data/docs-extensions-and-macros/macros/enterprise'
----

== enterprise_features

This block macro renders the licensing feature table for one scope from the enterprise features registry (see <<enterprise>>). Because the table is generated, it can never drift from the registry.

=== Usage

[,asciidoc]
----
enterprise_features::redpanda[]
enterprise_features::connect[]
enterprise_features::operator[title=Operator features,heading=What stops working]
----

The target is the scope: `redpanda`, `console`, `connect`, `operator`, or `cloud`. Rows render alphabetically by feature name with three columns: the feature name (linked to its documentation page when the entry has an `xref` or `url`), the description, and the expiration or restriction behavior. Named attributes:

title::
Optional table title override. The default is scope-specific, for example `Enterprise features in Redpanda`.

heading::
Optional third-column heading override. The default is `Behavior Upon Expiration` for the `redpanda` scope and `Restrictions Without Valid License` for the other scopes.

=== Registration

Registered together with the `enterprise` inline macro (see <<enterprise>>).

== prop

This inline macro references a Redpanda configuration property in prose. The property renders as a marked `<code>` element (`property-ref` class plus a `data-property-name` attribute) that the docs UI decorates with a hover-documentation tooltip. Marking is opt-in: only properties referenced through this macro get tooltips, so ambiguous words such as `admin` or `rack` in unrelated contexts (Helm values, feature settings) are never decorated by mistake.

The macro validates its target against the published property reference: the newest `redpanda-properties-<tag>.json` attachment in the `reference` module of the build, the same data the tooltips fetch at runtime. To migrate existing plain-backtick property mentions, use `doc-tools generate migrate-property-refs`.

=== Usage

[,asciidoc]
----
prop:cloud_storage_enabled[]
prop:iceberg_enabled[link=true]
prop:retention_ms[link=true,page=properties/topic-properties]
prop:write_caching_default[text=write caching]
----

The macro target is the property name. Named attributes:

link::
Set to `true` to also link the property to its reference page. The page is discovered dynamically: the macro indexes which reference-module page in the current component documents each property, by scanning property headings in the partials each page includes (respecting include tag filters such as `tags=redpanda-cloud`). Links are component-relative, so a Cloud page links to the Cloud component's own property pages, and they keep working if properties are split across different pages in the future. When discovery finds nothing, the page falls back deterministically to the property's `config_scope` (`cluster`, `broker`, or `topic`). This supersedes the `config_ref` macro's linking for most uses.

page::
Optional reference-page override (module-relative, without `.adoc`), for example `properties/object-storage-properties`. Overrides discovery entirely.

helm-path::
Set to `auto` to display the property as its Helm values path on pages rendered with the `env-kubernetes` attribute, so single-sourced content reads correctly for both Linux and Kubernetes audiences. The path is derived per property: `storage.tiered.config.<name>` for tiered storage properties, `config.node.<name>` for broker properties, and `config.cluster.<name>` for other cluster properties. On pages without `env-kubernetes`, the plain property name renders. This supersedes the deprecated `config_ref` macro's prefixing.

text::
Optional display text override. Wins over the Helm path display.

=== Configuration options

property-validate::
How to report a target that does not match any published property: `warn` (default) logs a build warning with the file path and close-match suggestions, `error` fails the build, and `off` disables validation. When no property JSON is available in the build, the macro renders without validation and logs a single warning.

property-ref-role::
CSS class applied to the code element. The default is `property-ref`.

=== Registration

[,yaml]
----
asciidoc:
  extensions:
    - '@redpanda-data/docs-extensions-and-macros/macros/prop'
----

== glossterm

The `glossterm` inline macro provides a way to define and reference glossary terms in your AsciiDoc documents.

NOTE: This macro is a customized version of https://gitlab.com/djencks/asciidoctor-glossary[`asciidoctor-glossary`].

=== Usage

Use the `glossterm` inline macro to reference a term within the text of the document:

[,asciidoc]
----
glossterm:my term[myDefinition]
----

It takes two parameters:

term::
The term to be defined.

definition (optional)::
The definition of the term. If the term is defined in the https://github.com/redpanda-data/docs-site[`shared` component] or the `local-terms` object of the `antora.yml` file, you can omit the definition as it will always be replaced by those definitions.

=== Configuration options

glossary-log-terms (optional)::
Whether to log a textual representation of a definition list item to the console.

glossary-term-role (optional)::
Role to assign each term. By default, glossary terms are assigned the `glossary-term` role, which gives them the class `glossary-term` in generated html.

glossary-links (optional)::
Whether to generate links to glossary entries.
By default, links to the glossary entries are generated from the glossary terms. To avoid this, set the attribute to `false` as either asciidoctor configuration or a header attribute.

glossary-page (optional)::
Target page for glossary links. By default, links are generated to the same page as the glossary term. To specify the target page, set this attribute to the resource ID of a page where the `glossary` block macro is used.

glossary-tooltip (optional)::
Whether to enable tooltips for the defined terms. Valid values are:
- title: This uses the browser built-in `title` attribute to display the definition.

- true: This inserts the definition as the value of the attribute `data-glossary-tooltip`.

- data-<attribute-name>​: This inserts the definition as the value of the supplied attribute name, which must start with `data`.

The last two options are intended to support js/css tooltip solutions such as tippy.js.

=== Registration

[,yaml]
----
asciidoc:
  extensions:
    - '@redpanda-data/docs-extensions-and-macros/macros/glossary'
----

== helm_ref

This is an inline macro to create links to a Helm `values.yaml` file on ArtifactHub.

=== Usage

In an AsciiDoc document, use the `helm_ref` macro as follows:

[,asciidoc]
----
helm_ref:<helmRef>[]
----

Where `<helmRef>` is the Helm configuration value you want to reference in the `values.yaml` file.

For example:

Given a Helm reference value of `myConfigValue`, you would use the macro like this:

[,asciidoc]
----
helm_ref:myConfigValue[]
----

This will generate the following output:

[,asciidoc]
----
For default values and documentation for configuration options, see the https://artifacthub.io/packages/helm/redpanda-data/redpanda?modal=values&path=myConfigValue[values.yaml] file.
----

If you do not specify a Helm reference value, the macro generates a link without specifying a path.

=== Registration

[,yaml]
----
asciidoc:
  extensions:
    - '@redpanda-data/docs-extensions-and-macros/macros/helm-ref'
----

== iceberg-explorer

This macro registers an `[iceberg-explorer]` block that emits a version-aware mount point for the interactive Iceberg Mode Explorer:

[,html]
----
<div class="iceberg-explorer-mount" data-iceberg-explorer="1" data-version="26.2">
  <p class="iceberg-explorer-fallback">Interactive Iceberg Mode Explorer. If this text is still here...</p>
</div>
----

The block renders the container only. The explorer UI and its translation engine live in the docs-ui bundle, which hydrates the mount point, so the block is inert unless the site uses a docs-ui build that includes the explorer. This is the same "macro emits container, docs-ui hydrates it" handshake used by the Redpanda Connect component metadata block.

Until the explorer module replaces the container's contents, the fallback paragraph is visible. It is ordinary markup rather than `<noscript>` on purpose: the failure readers are most likely to hit is JavaScript running normally on a site whose UI bundle has no explorer module, and a browser hides `<noscript>` in that case, leaving a zero-height blank space with no explanation.

The page's component version (`page-version`, falling back to `page-component-version`) is stamped onto the mount point as `data-version` so the UI can load the engine build that matches the doc version. If neither attribute is set, `data-version` is omitted.

Antora derives both attributes from the component version and locks them, so a page header cannot set them: an unversioned component (`version: ~`, which is what this repo's preview site uses) emits no `data-version`, and docs-ui falls back to its own version detection.

=== Mount contract

docs-ui must hydrate on the `data-iceberg-explorer` attribute (`[data-iceberg-explorer]`), never on a class name that matches the block name.

Asciidoctor turns an unrecognized block style into a CSS class. A site that uses `[iceberg-explorer]` but whose playbook does not register this macro still publishes `<div class="openblock iceberg-explorer">`, with the author's JSON body dumped onto the page as a code listing. If the explorer module hydrated on `.iceberg-explorer`, that accident would render as a working-looking explorer filled with built-in sample data, the author's defaults silently discarded, and no error anywhere to trace it back to the missing playbook entry.

Only this macro can emit a data attribute, so:

* `data-iceberg-explorer` is the mount contract, and its value is the contract version (`1` today). Bump it only if the emitted attributes change shape.
* `iceberg-explorer-mount` is a styling hook, not a mount signal.

The constants are exported (`MOUNT_ATTRIBUTE`, `MOUNT_CONTRACT_VERSION`, `MOUNT_CLASS`, `MOUNT_SELECTOR`) so docs-ui and the tests can assert against one definition.

=== Usage

```asciidoc
[iceberg-explorer]
--
--
```

Set the initial configuration with the `config` attribute:

```asciidoc
[iceberg-explorer,config="key:mode=binary;value:mode=binary"]
--
--
```

Or pass a JSON object as the block body to supply author-defined defaults:

```asciidoc
[iceberg-explorer]
----
{
  "config": "value:mode=schema_latest"
}
----
```

The explorer module reads only the `config` key and renders its own sample schema and record. Other keys are forwarded verbatim in `data-defaults` and ignored, so do not document author-supplied schemas or records as supported until docs-ui reads them.

The JSON is attribute-escaped and emitted as `data-defaults`. The body must be a JSON *object*: `JSON.parse()` also accepts scalars and arrays, and docs-ui reads keys off the parsed value, so a bare `123` is as unusable as a syntax error. If the body is not a JSON object, the macro logs a warning that names the page, omits `data-defaults`, and still renders the mount point.

The block accepts an open (`--`), listing (`----`), literal, or pass body. It is not registered for the paragraph context, because the processor replaces the block with the mount point: registering paragraphs would delete the prose under a stray `[iceberg-explorer]` line from the published page.

|===
| Attribute | Description

| `config`
| Initial configuration string. Emitted as `data-config`. Falls back to the `config` key of the JSON body.

| `height`
| Minimum height for the container, emitted as an inline `min-height` style. A bare number is treated as pixels (`height=400` becomes `min-height:400px`). Otherwise the value must be a CSS length in `px`, `rem`, `em`, `vh`, `vw`, or `%`; any other value is rejected with a warning rather than interpolated into the style attribute.

| `engine-base`
| Optional base location for the translation engine build, emitted as `data-engine-base`. docs-ui falls back to its own default when this is absent, so set it only to pin a specific engine build.
|===

=== Registration

[,yaml]
----
asciidoc:
  extensions:
    - '@redpanda-data/docs-extensions-and-macros/macros/iceberg-explorer'
----

=== docs-ui dependency

This block is half of a two-repo handshake and does nothing on its own. The explorer UI and its translation engine ship in docs-ui, and no released docs-ui bundle contains them yet: the explorer module is still open in `redpanda-data/docs-ui` (PR #404, `jake/iceberg-mode-explorer`), so on a site built with the current bundle the block renders the container and its fallback paragraph, nothing more.

Order of operations before an author uses the block on a published page:

. Merge and publish this package, so consumers can resolve the macro.
. Merge and release docs-ui #404, with hydration keyed on `[data-iceberg-explorer]` (see <<Mount contract>>).
. Add the macro to each consuming playbook's `asciidoc.extensions` (`redpanda-data/docs`, `cloud-docs`). Registering it in this repo's `local-antora-playbook.yml` covers only this repo's preview site.

Until step 2 lands, a page that uses the block shows the fallback paragraph rather than an explorer. That is deliberate: it is visible, so a missing or outdated UI bundle looks broken rather than looking like a page with nothing on it.
