= AsciiDoc macros reference
:toc:

Reference documentation for all AsciiDoc macros and extensions provided by this library.

IMPORTANT: Be sure to register each extension under the `asciidoc.extensions` key in the playbook, not the `antora.extensions` key.

This extension adds the necessary classes to make line numbers and line highlighting work with Prism.js.

== config_ref

IMPORTANT: `config_ref` is deprecated. The `prop` macro supersedes all of its functionality: it validates names against the published property reference, discovers the target page dynamically instead of taking a manual path, powers hover tooltips, and its `helm-path=auto` attribute replaces `config_ref`'s Kubernetes prefixing with a per-property correct Helm values path (`config_ref` prefixed every property with `storage.tiered.config.`, mislabeling non-tiered properties). Migrate call sites with `doc-tools generate migrate-property-refs --config-refs`. The macro stays registered only because older versioned docs, which are frozen, still contain it; generated content emits `prop` (the extractor rewrites any `config_ref` it finds).

This inline macro is used to generate a reference to a configuration value in the Redpanda documentation. The macro's parameters allow for control over the generated reference's format and the type of output produced.

=== Usage

The `config_ref` macro is used in an AsciiDoc document as follows:

[,asciidoc]
----
config_ref:configRef,isLink,path[]
----

The `config_ref` macro takes three parameters:

configRef::
This is the configuration reference, which is also used to generate the anchor link if `isLink` is `true`.

isLink::
Whether the output should be a link. If `isLink` is set to `true`, the output will be a cross-reference (xref) to the relevant configuration value.

path::
This is the path to the document where the configuration value is defined. This parameter is used to to generate the link if `isLink` is `true`.

IMPORTANT: The path must be the name of a document at the root of the `reference` module.

NOTE: The `config_ref` macro is environment-aware. It checks if the document it is being used in is part of a Kubernetes environment by checking if the `env-kubernetes` attribute is set in the document's attributes. Depending on this check, it either prepends `storage.tiered.config.` to the `configRef` or just uses the `configRef` as is.

For example:

[,asciidoc]
----
config_ref:example_config,true,tunable-properties[]
----

=== Registration

[,yaml]
----
asciidoc:
  extensions:
    - '@redpanda-data/docs-extensions-and-macros/macros/config-ref'
----

== enterprise

This inline macro marks a feature as an enterprise feature in prose. The feature name renders as a uniquely styled term with a tooltip explaining that the feature requires an Enterprise Edition license, and links to the feature's documentation or to the licensing page.

The macro validates its target against the enterprise features registry: `modules/ROOT/partials/enterprise-features.yml` in the `shared` component (the `shared/` folder of the docs repository). The registry is the canonical list of enterprise features and their approved external names. Targets are matched case-insensitively, including aliases, and the canonical name, feature page link, and tooltip come from the matching entry. A target that matches no entry is reported according to `enterprise-validate` and renders as plain text -- no styling, tooltip, or link, since there is nothing verified to style it with. To mark a new feature as enterprise, add it to the registry first.

=== Usage

[,asciidoc]
----
enterprise:Continuous Data Balancing[]
enterprise:Tiered Storage[xref=manage:tiered-storage.adoc]
enterprise:Audit Logging[text=audit logging]
enterprise:Iceberg Topics[tooltip=Iceberg Topics requires an Enterprise Edition license and object storage.]
----

The macro target is the feature name, which can contain spaces. Named attributes:

xref::
Optional Antora resource ID of the feature's documentation page. Overrides the registry entry's link. When neither is set, the term links to the licensing page.
+
Registry entries can carry a Kubernetes-specific page: on pages with the `env-kubernetes` attribute the entry's `xref-kubernetes` is used, and otherwise the entry's default `xref` (the Linux or generic self-managed page). This mirrors the `config_ref` macro's environment awareness. There is no Cloud counterpart -- see <<cloud-pages>>.

text::
Optional display text override. Use it when the sentence needs different casing or phrasing than the feature name.

tooltip::
Optional tooltip text override. Overrides the registry entry's `tooltip`. The default is `<feature> requires an Enterprise Edition license.`

=== Configuration options

enterprise-validate::
How to report a target that does not match any registry entry: `warn` (default) logs a build warning with the file path and close-match suggestions, `error` fails the build, and `off` disables validation. When no registry is available in the build, the macro renders without validation and logs a single warning.

enterprise-licensing-page::
Resource ID of the licensing page used when no `xref` attribute is given. The default is `get-started:licensing/overview.adoc`.

enterprise-feature-role::
CSS class applied to the wrapping span. The default is `enterprise-feature`. Style this class in the UI bundle to give enterprise terms a consistent visual treatment.

enterprise-tooltip::
Controls the tooltip attribute: `title` (default), `true` (renders `data-enterprise-tooltip` for UI-driven tooltips), any attribute name starting with `data-`, or `false` to disable tooltips.

enterprise-links::
Set to `false` to render the term without a link.

enterprise-beta-badge::
Set to `false` to suppress the beta badge in prose. Generated tables always show it. See <<beta-features>>.

[[cloud-pages]]
=== Cloud pages

Redpanda Cloud has no Enterprise Edition license -- customers never apply or manage one -- so a page in a Cloud component (recognized by its `env-cloud` attribute) has nothing true to say about a license, its expiration, or its restrictions. On such a page the macro renders the target as plain text with no styling, tooltip, or link, skipping registry validation and the release-status checks below entirely, and reports the mention according to `enterprise-validate`.

This also covers the Cloud rendering of single-sourced self-managed prose: `env-cloud` is read from the document being converted, which reflects the page actually being rendered (the Cloud stub page), regardless of which repo the included `enterprise:` mention was written in. See the `prop` macro's <<prop-availability>> for the same mechanism applied to properties.

The `enterprise_features` block macro is affected too: see <<cloud-pages-block>>.

[[release-status]]
=== Release status

A registry entry's `status` field declares where a feature may be referenced. It is the enterprise equivalent of `cloud_supported` for properties: one field in the data, checked at build time, rather than a rule reviewers have to remember.

[cols="1,3a"]
|===
| `status` | Behavior

| `ga` (default)
| Shipped. Referenced anywhere, no badge. Applies when `status` is absent, so existing entries need no change.

| `beta`
| Publicly available as a beta. Referenced anywhere, with a `beta` badge in prose and in the generated tables.

| `unreleased`
| In a release candidate only, not public. Referenced *only* from a prerelease component version. On a released page the mention renders as plain text with no enterprise styling, tooltip, or link, and the build reports it according to `enterprise-validate`. Omitted from `enterprise_features` tables on released pages; listed with its badge on prerelease pages.
|===

A prerelease page is one whose component version sets `prerelease` in `antora.yml`. A playbook can declare it directly with the `page-component-version-is-prerelease` document attribute.

`beta: true` predates this field and still means `status: beta`, so old entries keep working. Prefer `status` in new entries, because a boolean cannot express "not public at all". An unrecognized `status` value is reported rather than silently treated as shipped. Use `status-tooltip` to override the `unreleased` badge's hover text.

For the writer-facing procedure, see link:DOCUMENTING_UNRELEASED_FEATURES.adoc[Documenting properties and enterprise features before they ship].

[[beta-features]]
=== Beta features

Add `beta: true` to a registry entry to mark the feature as beta. The macro then renders a beta badge after the feature name, both in prose and in the generated `enterprise_features` tables, so one registry field keeps every reference consistent:

[,yaml]
----
- name: Stretch Clusters
  scope: operator
  beta: true
  feature-suffix: (StretchCluster resource)
----

Add `beta-tooltip` to give the badge hover text.

Do not write a `badge:` macro call into `feature-suffix` to achieve this. The badge is emitted as an inline passthrough, so it renders whether or not the consuming playbook registers the `badge` macro, and it degrades to the text `(beta)` in Markdown. A hand-written macro call renders as literal source text in any build that does not register that macro.

=== Markdown output

In HTML, the enterprise signal is carried by the span's CSS class and its tooltip attribute. Both are attributes, so an HTML-to-Markdown conversion drops them and the term arrives as an ordinary feature name. To keep the signal for readers of the Markdown pages, including AI agents, the `convert-to-markdown` extension appends an explicit `(enterprise)` marker and preserves any link:

[,markdown]
----
Enable [Tiered Storage](../manage/tiered-storage.md) (enterprise) today.
----

A feature that is also marked `beta: true` gets one combined marker rather than two adjacent parentheticals:

[,markdown]
----
Enable [Stretch Clusters](../deploy/stretch-clusters.md) (enterprise, beta) today.
----

This applies to the inline macro. The tables from `enterprise_features` need no enterprise marker, because their expiration column already states the licensing behavior as text. A beta badge in a table converts to `(beta)` on its own.

=== Registration

[,yaml]
----
asciidoc:
  extensions:
    - '@redpanda-data/docs-extensions-and-macros/macros/enterprise'
----

== enterprise_features

This block macro renders the licensing feature table for one scope from the enterprise features registry (see the `enterprise` macro above). Because the table is generated, it can never drift from the registry.

=== Usage

[,asciidoc]
----
enterprise_features::redpanda[]
enterprise_features::connect[]
enterprise_features::operator[title=Operator features,heading=What stops working]
----

The target is the scope: `redpanda`, `console`, `connect`, or `operator`. Rows render alphabetically by feature name with three columns: the feature name (linked to its documentation page when the entry has an `xref` or `url`), the description, and the expiration or restriction behavior. Named attributes:

title::
Optional table title override. The default is scope-specific, for example `Enterprise features in Redpanda`.

heading::
Optional third-column heading override. The default is `Behavior Upon Expiration` for the `redpanda` scope and `Restrictions Without Valid License` for the other scopes.

[[cloud-pages-block]]
There is no `cloud` scope: Redpanda Cloud has no Enterprise Edition license, so there is no licensing table to generate for it (see <<cloud-pages>>). Calling this macro from a page in a Cloud component -- directly or through single-sourced self-managed content -- renders nothing: no table and no admonition. The diagnostic goes to the build log, reported according to `enterprise-validate` and naming the page, so it reaches the writer and never the reader.

=== Registration

Registered together with the `enterprise` inline macro.

== prop

This inline macro references a Redpanda configuration property in prose. The property renders as a marked `<code>` element (`property-ref` class plus a `data-property-name` attribute) that the docs UI decorates with a hover-documentation tooltip. Marking is opt-in: only properties referenced through this macro get tooltips, so ambiguous words such as `admin` or `rack` in unrelated contexts (Helm values, feature settings) are never decorated by mistake.

The macro checks that a property is actually available to the audience reading the page, and links it only where a page documents it. It validates against the published property data: a `redpanda-properties-<tag>.json` attachment in the `reference` module, the same data the tooltips fetch at runtime. See <<prop-availability>> for which properties each doc set may reference and <<prop-version-selection>> for which file a given page uses. To migrate existing plain-backtick property mentions, use `doc-tools generate migrate-property-refs`. To render a property's value (its default, minimum, unit, and so on) rather than its name, use <<propval>>. For `rpk` flag and Connect field values, see <<rpkval>> and <<connectval>>; for a linked `rpk` command, see <<rpkcmd>>.

=== Usage

[,asciidoc]
----
prop:cloud_storage_enabled[]
prop:iceberg_enabled[link=true]
prop:retention.ms[link=true,page=properties/topic-properties]
prop:cloud_storage_enabled[link=true,page=cloud:reference:properties/cluster-properties]
prop:write_caching_default[text=write caching]
----

The macro target is the property name. Named attributes:

link::
Set to `true` to also link the property to its reference page. The page is discovered dynamically: the macro indexes which reference-module page in the current component documents each property, by scanning property headings in the partials each page includes (respecting include tag filters such as `tags=redpanda-cloud`). Discovered links are component-relative, so a Cloud page links to the Cloud component's own property pages, and they keep working if properties are split across different pages in the future. See <<prop-availability>> for properties the current component does not document. This supersedes the `config_ref` macro's linking for most uses.

page::
Optional reference-page override, without `.adoc`. Overrides discovery entirely, and is never build-verified either way, so it may name any page that documents the property. A bare name (`properties/object-storage-properties`) stays module-relative within `reference` in the current component; qualify it with a module (`guides:cloud/object-storage`) or a component and module (`cloud:reference:properties/cluster-properties`) to point elsewhere.

helm-path::
Set to `auto` to display the property as its Helm values path on pages rendered with the `env-kubernetes` attribute, so single-sourced content reads correctly for both Linux and Kubernetes audiences. The path is derived per property: `storage.tiered.config.<name>` for properties whose name begins `cloud_storage_`, `config.node.<name>` for broker properties, and `config.cluster.<name>` for cluster properties. Topic properties render as the plain name, because they are set per topic through the Kafka API, rpk, or a Topic resource and have no `values.yaml` key at all. The plain name also renders on any page where `env-kubernetes` is unset or explicitly `false`. This supersedes the deprecated `config_ref` macro's prefixing.

text::
Optional display text override. Wins over the Helm path display.

=== Configuration options

property-validate::
How to report a target that does not match any published property: `warn` (default) logs a build warning with the file path, the dataset the page was checked against, and close-match suggestions; `error` fails the build; and `off` disables validation and silences the unknown-name, unavailable-property, unpublished-property and missing-data warnings. Diagnostics about the build itself are not silenced by `off`, because they report a broken input rather than a questionable mention: unusable property JSON, a property claimed by two declared sources, and an index built after conversion started. When no property JSON is available in the build, the macro renders without validation and logs one warning per component version.

[[prop-version-selection]]
=== Which property data a page validates against

Each published Redpanda release series ships its own `redpanda-properties-v<major>.<minor>.<patch>.json`, so a page must be checked against the data for *its own* series. A 25.3 page validated against 26.2 data would accept properties that release never had and flag removed ones as typos.

The macro therefore selects by series (`major.minor`) rather than by newest tag:

. For a component version with a numeric series (`streaming` at `25.3`), the newest patch whose tag matches that series -- preferring the copy attached to the page's own version, then the same series published anywhere in the component, since a series' JSON sometimes lives only on the main branch. Patch numbers compare numerically, so `v25.3.11` beats `v25.3.2`.
. For a Cloud component (`env-cloud`), the newest `streaming` dataset, then `ROOT`. Cloud is managed Redpanda and always tracks the current release, so its own version is never consulted.

Selecting by series rather than newest tag matters in practice: the docs repo's main branch carries the previous series' JSON alongside its own, and a prerelease tag could land there too. Newest-tag-wins would hand that file to pages of a different release. A component with no property data and no `env-cloud` attribute gets no dataset at all -- see <<prop-availability>>.

Tags compare by release precedence, so a GA release outranks its own release candidates and `rc2` outranks `rc1`. A cycle publishes `v26.3.1-rc1`, then `rc2`, then the GA `v26.3.1`, and a beta branch at `version: 26.3` lands on the newest of those deterministically rather than on whichever file the content catalog happened to yield first. Redpanda spells prereleases as one identifier (`-rc2`, not `-rc.2`), which the semver spec compares as a string, so the trailing digits are split out before comparing; otherwise `rc10` would sort below `rc2`.

Cloud takes the newest *GA* dataset and ignores prereleases entirely, because Cloud runs released Redpanda. An RC published on a beta branch outranks the current GA by version number, so without this every Cloud page would start validating against an unreleased property list. When a build contains only prerelease data, Cloud goes unvalidated and the warning says so specifically rather than reporting no data at all.

When a component publishes property data for other series but none for the page's own, the macro declines to validate rather than use a neighbouring release's data. It logs one warning per component version naming the missing file, the tags it did find, and the `doc-tools generate property-docs --tag` command that produces it. `prop:` targets on those pages render unvalidated and their tooltips carry no data, so either generate the series' JSON on that branch or leave `prop:` out of that version's content.

property-ref-role::
CSS class applied to the code element. The default is `property-ref`.

[[prop-availability]]
=== Which properties a doc set may reference

Property data exists for two doc sets.

*Self-managed (`streaming`)* publishes its own properties JSON per release, as a reference-module attachment. Every property in that release's file is available.

*Cloud* is managed Redpanda, so it has no property data of its own and always tracks the newest self-managed file. A Cloud component is recognized by its `env-cloud` attribute.

A *cluster* property is available to Cloud unless its `cloud_supported` field is explicitly `false`. That field is the union of the Cloud states -- no published property is `cloud_editable` or `cloud_readonly` without also being `cloud_supported` -- so it is the single gate for that scope.

*Topic and broker* properties are not gated by it. `cloud_supported` is derived from the Cloud control plane's install pack, whose two sections (`customer_managed_configs` and `readonly_cluster_config`) describe cluster configuration and contain nothing else: every entry resolves to a cluster property, and no topic property appears anywhere in the file. A `false` value on another scope therefore asserted something that source cannot know, while Cloud users set topic properties routinely through the Kafka API and Console and Cloud publishes a topic properties reference of its own. The property extractor no longer writes the field for other scopes, and the macro treats an absent value as "no opinion", so already-published datasets stay correct too.

Any other component (`connect`, the agentic data plane, a preview site) has no property data, and none is inferred for it. Those components carry their own product versions, which say nothing about which Redpanda properties exist, so a version number is never read as a Redpanda release. Supporting a further doc set is a deliberate addition to the macro.

When a property is not available to the page's audience -- a non-`cloud_supported` property on a Cloud page -- the macro renders it as plain `<code>`: no link, no `data-property-name` marker, and therefore no tooltip. A tooltip would imply the reader can set something they cannot. The build logs a warning naming the property, the file, and the dataset consulted. Fix `cloud_supported` in the property extractor if the data is wrong; otherwise reword the sentence and drop the macro.

When no dataset covers the component at all, the macro warns once per component version and renders every `prop:` target as plain code, rather than emitting tooltips it could not verify.

=== Linking

`link=true` links the property to its reference page, but only when a page *in the same component* documents it. Nothing is linked across components, and no target is guessed from the property's `config_scope`: a link the build cannot verify is a broken link. An available property that no page renders -- a deprecated property, or one held back by include tags -- keeps its tooltip and renders unlinked; `link=true` warns in that case. Use `page=` to set a target explicitly for one mention.

[[prop-property-source]]
==== Declaring which page is the reference

A reference page can declare the property collection it publishes:

[,asciidoc]
----
= Cluster Configuration Properties
:page-property-source: cluster-properties
----

Claims on a property are then ranked, highest first:

. A page that declares `page-property-source`.
. A property heading pulled in from a generated partial.
. A bare heading on a page that happens to match a property name.

The ranking exists because inference alone is ambiguous. Several real property names are ordinary words -- `admin`, `brokers`, `rack`, `retries`, `superusers` -- so any reference page titled or sectioned with one of those would otherwise claim the property from the page that documents it, and a page title generates no anchor, so both the link and the tooltip URL would point at nothing. Ranking also makes resolution independent of the order Antora aggregates content, which is stable for one checkout but carries no meaning.

Within a rank, the first page wins, ordered by path so the result is deterministic. When two *declared* pages claim the same property the build warns and names both: that is an authoring conflict rather than something to resolve quietly.

Declaring the attribute is optional. Existing pages keep working through inference, and the declaration is worth adding when a property could plausibly be claimed by more than one page in the component, or to state the intent explicitly rather than relying on the generated partials happening to win.

=== Registration

[,yaml]
----
asciidoc:
  extensions:
    - '@redpanda-data/docs-extensions-and-macros/macros/prop'
----

== propval

This inline macro renders one value from the property data as plain text, so a sentence such as "defaults to 2 weeks" is generated from the same data as the property reference instead of typed by hand. Hand-typed values drift when a release changes a default, and nothing catches it.

[,asciidoc]
----
Set prop:log_segment_ms[], which defaults to propval:log_segment_ms[default].
The minimum is propval:log_segment_ms[min].
Changing prop:cloud_storage_enabled[] requires a restart: propval:cloud_storage_enabled[restart].
The exact default is `propval:log_segment_ms[default,format=raw]`.
----

Rendered against `redpanda-properties-v26.2.4.json`, those lines read: "defaults to 2 weeks", "The minimum is 1 minute", "requires a restart: yes", and "The exact default is `1209600000`".

`propval:` is registered by the `prop` macro's extension, so a playbook that registers `macros/prop` has both, along with <<rpkval>>, <<connectval>> and <<rpkcmd>>. It shares every data decision with `prop:` rather than copying them: the same dataset for the page's version (<<prop-version-selection>>), the same `property-validate` modes, the same Cloud availability gate (<<prop-availability>>), and the same refusal to use a neighbouring release's data when a version has none.

=== Usage

The target is the property name. The first positional attribute (or `field=`) names the field, and defaults to `default`. Every value macro shares one set of field names (<<value-fields>>), so `introduced`, `values` and `description` mean the same thing in `propval:`, `rpkval:` and `connectval:`.

[[propval-fields]]
[cols="1,2,2"]
|===
| Field | Source in the property JSON | Example (v26.2.4)

| `default`
| `default`, formatted as the reference table formats it. The human-readable form is the table's parenthetical (`default_human_readable`) when the data has one.
| `log_segment_ms`: `2 weeks`; `fetch_max_bytes`: `55 MiB`; `cloud_storage_enabled`: `false`; `node_id`: `null`

| `type`
| `type`
| `integer`

| `unit`
| `units`, else the unit the table derives from the name suffix (`_ms`, `_bytes`, and so on)
| `milliseconds`

| `min`, `max`
| `minimum`, `maximum`, humanized with the unit
| `log_segment_ms` min: `1 minute`

| `restart`
| `needs_restart`
| `yes` or `no`

| `nullable`
| `nullable`
| `yes` or `no`

| `values`
| `enum` (or `items.enum` for arrays), each value as inline code, because some values contain commas
| `none`, `delete`, `compact`, `compact,delete`

| `scope`
| `config_scope`
| `cluster`, `broker`, or `topic`

| `introduced`
| `version`
| `v26.1.1`

| `visibility`
| `visibility`
| `user`, `tunable`

| `restored`
| `gets_restored` (restored on Whole Cluster Restore)
| `yes` or `no`

| `aliases`
| `aliases`
| comma-separated names

| `cloud-access`
| `cloud_editable` and `cloud_readonly`, for cluster properties only
| `editable`, `read-only`, or `not available`

| `description`

| `log_segment_ms`: "Default lifetime of log segments. ..."

| `examples` (alias `example`)
| `example`, as AsciiDoc. Inline only when it is one paragraph, such as `` `true` ``; a YAML example needs `propval::`
| `admin_api_require_auth`: `true`

| `see-also` (aliases `see_also`, `seeAlso`)
| `see_also`, the reference's Related topics row, with only the items for this surface (`cloud_only` and `self_managed_only`)
| `log_segment_ms`: a link to `segment.ms`

| `deprecated` (alias `is_deprecated`)
| `is_deprecated`
| `yes` or `no`

| `enterprise` (alias `is_enterprise`)
| `is_enterprise`. Hidden on Cloud, where the reference shows no license note
| `yes` or `no`

| `secret` (alias `is_secret`)
| `is_secret`
| `yes` or `no`

| `category`
| `category`, the include tag the reference pages filter on
| `tiered-storage`, `schema-registry`
|===

The JSON key names and table labels also work as field names: `minimum`, `maximum`, `needs_restart`, `units`, `enum`, `config_scope`, `version`, `gets_restored`. So do the aliases every value macro shares, such as `since` for `introduced` and `options` for `values`. A field name `propval:` does not support is a warning (an error with `property-validate: error`) that lists the fields it does.

format::
`human` (default) or `raw`. `raw` gives the exact value: the code value in the reference table for `default`, the plain number for `min` and `max`, `true` or `false` for the yes-or-no fields, and a JSON array for `values` and `aliases`.

The output is a `<span>` with the stable class `property-value` and `data-property` and `data-field` attributes. It is plain text with no tooltip; mark the name with `prop:` for that. The macro works inside backticks, so `` `propval:x[default,format=raw]` `` renders as inline code. Don't put `values` inside backticks: it already renders each value as inline code, and backticks would nest one code element inside another.

A description, an example or a Related topics list that is longer than one paragraph has no inline form. Write the block form on a line of its own, which parses the text into the page (<<value-text>>):

[,asciidoc]
----
propval::cleanup.policy[description]
----

It renders an open block with the roles `property-value` and `property-value-<field>`. Any other field in the block form renders as a paragraph of its own.

=== Formatting

Values come from the reference generator's own helpers, so prose and the reference tables cannot disagree:

* `default` uses `formatPropertyValue`, the helper that renders the table's Default cell. In the human form, a duration uses the table's parenthetical when the data has one.
* A duration with no parenthetical in the data is humanized by a port of the extractor's `format_time_human_readable`, the function that produced the parenthetical: the largest unit that divides the value evenly, else the value in its own unit (`1500 milliseconds`).
* A byte count renders in IEC units (`128 MiB`) only when the table's Unit row says bytes and the value is an exact multiple. Otherwise the exact number renders. `log_segment_size` and `segment.bytes` have no unit in the data or the table, so they render `134217728`. Adding `units` for them belongs in the property extractor, not in prose.
* Negative numbers are sentinels (`-1` for unlimited) and render as written.
* `null`, an empty string, and booleans render as the table renders them: `null`, `null`, `true`, `false`.
* A topic property that the data leaves unset, such as `retention.bytes`, renders `null` for `default`, as the table does. The topic inherits its cluster property (`corresponding_cluster_property` in the data), so in prose, point to that property with `prop:`, such as "inherits prop:retention_bytes[]", rather than saying the default is `null`.

=== Failures

A value has no safe fallback, so whenever the build cannot verify one, `propval:` renders a visible placeholder such as `<unknown default>` (class `property-value property-value-unknown`) and logs why, naming the property, the field, and the dataset. It never renders a guessed value. The cases:

* The page's version has no property data, or the component has none (the same diagnostic `prop:` logs, plus one for the `propval:` call).
* The property is not in the page's dataset.
* The property is not available on a Cloud page (`cloud_supported: false` on a cluster property).
* The field is not one `propval:` supports.
* The property has no such field in the data, for example `max` on a property with no maximum, or `default` on a deprecated property the data gives no default.
* The value is an integer beyond JavaScript's exact range (the 2^64^-1 sentinel of `virtual_cluster_min_producer_ids`), which `JSON.parse` has already rounded.
* On a Cloud page, the field is one the Cloud property reference does not show: `default`, `introduced`, `visibility`, `restored`, and `aliases`. The reference renders those only outside `env-cloud` (Cloud shows "Available in the Redpanda Cloud Console" in the Default row), so a Cloud page cannot state them either. Put the sentence in an `ifndef::env-cloud[]` block, or use a field the Cloud reference shows, such as `cloud-access`.

With `property-validate` set to `error`, an unknown property, an unsupported field, a field the property does not have, a property not available on Cloud, or a field the Cloud reference does not show fails the build. The last two appear only in the Cloud build, so cloud-docs needs `property-validate: error` to catch single-sourced prose that would render a placeholder. With `off`, the placeholder is still rendered and still reported, because `off` means "do not check names", and a silent `<unknown default>` would reach readers unnoticed.

=== Migrating hand-written values

To run these checks together with the rpk and Connect checks, and fail CI on them, use <<check-reference-values>>.

`doc-tools generate migrate-property-values` finds hand-written values next to a property mention ("defaults to X", "the default is X", "default: X", "minimum X", "is X by default") and checks each against the data for the repo's own version, selected exactly as `prop:` selects it. It writes a JSON and a Markdown report. Each finding is one of:

exact:: The written text is what `propval:` renders. Auto-safe when the statement is in the same sentence as its property, no other property is named in that paragraph line or its list entry, the data value is not null, and the file is not release or upgrade notes. On a self-managed page, a `default` (or another field the Cloud reference hides), or any field of a property Cloud does not support, is auto-safe only inside `ifndef::env-cloud[]` or in a page (not a partial) with no `tag::` regions. Otherwise the page may be single-sourced into cloud-docs, where `propval:` renders a placeholder, so the finding is proposed only: wrap the sentence in `ifndef::env-cloud[]` first.
equivalent:: Same value, different wording (`7 days` and `1 week`). Proposed, never applied.
mismatch:: The written value differs from the data. Likely a doc error. Never applied.
unset:: The data default is null (not set), but the prose states a value. Redpanda often computes a fallback at runtime for an unset property, such as 10% of free disk for `compaction_ctrl_backlog_size`, so confirm the value in the source. Never applied.
unverifiable:: Not comparable: unparseable, a field the property does not have, a sentence qualified to another audience or release ("In Redpanda Cloud", "in earlier versions", "If the default is"), content inside `ifdef::env-cloud[]` on a self-managed page, a Cloud default, or "no default" for a topic property, which inherits its cluster property.
example-output:: A value shown in command output inside a listing, literal, or fenced block. These findings are counted and listed apart from prose findings, and never applied. Each has a verdict: `stale`, `matches`, or `unverifiable` with a reason.

Tables are scanned too. A statement in a cell belongs to the property that opens the row or cell, and a `Default` column states the default of the row's property. Table findings are reported but never applied.

`--write` applies only auto-safe exact matches. The tool skips prose inside code blocks, headings, attribute entries, comment lines, `ifndef::env-cloud[]` content on a Cloud page, and generated content. For cloud-docs, pass the docs checkout with `--lender` so Cloud can borrow its GA data.

[,bash]
----
npx doc-tools generate migrate-property-values --docs-dir . --report-dir ./propval-report
npx doc-tools generate migrate-property-values --docs-dir ../cloud-docs --lender . --report-dir ./propval-report-cloud
----

==== Example output

The tool reads these output shapes: `rpk topic describe` config tables (`KEY VALUE SOURCE`), `name=value (SOURCE)` lines, `kafka-configs --describe` lines (the first synonym's source), Key/Value/Source records in JSON or YAML (debug bundles, Topic resource status), `rpk cluster config get` output in the same block or an Input/Output pair, `rpk cluster config export` YAML, and Admin API `/v1/cluster_config` JSON. `rpk cluster config status` output states no values. A topic property is compared with the cluster property it inherits, taken from the data's `corresponding_cluster_property`, or `alternate_cluster_property` when the same output shows `cleanup.policy` set to compact. A Kafka broker alias such as `log.segment.bytes` is not in the data, so the Redpanda-named synonym row is compared. Values are compared exactly as raw bytes, milliseconds, booleans, or enum text. `-1` matches a limit that the data leaves unset.

A row is compared only when it asserts the default. A row with source `DEFAULT_CONFIG` or `DEFAULT` asserts it. Output with no source column (`config get`, `export`, Admin API) asserts it only when the text just before the block mentions the default. The following are `unverifiable`, with the first matching reason:

* `not-default-source`: Another source, such as `DYNAMIC_TOPIC_CONFIG` or `STATIC_BROKER_CONFIG`.
* `ifdef::env-cloud` on a self-managed page, or `cloud-default` on a Cloud page.
* `set-earlier-on-page`: The page sets the cluster property before the block, as `name=value`, `name: value` (including Helm `config.cluster.name`), or `rpk cluster config set name value`. A topic-level override doesn't count, because it would change the row's source.
* `helm-operator-context`: A Kubernetes page (`kubernetes/` path or `k-` file name), or a command run through `kubectl` or `helm`. The chart or operator may set the value.
* `dev-or-bootstrap-config`: The page starts Redpanda in `dev-container` mode, with `rpk container start`, or from a bootstrap file.
* `current-value`: Output with no source column, and no mention of the default before it.
* `unset-in-data` or `not-comparable`.

The report lists stale examples in their own table. It lists unverifiable rows whose value differs from the default in a context that may set them (other than `not-default-source`) for a human to check.

== rpkval

This inline macro renders one value of an `rpk` flag from the published rpk data, so a sentence such as "the default is -1" comes from the same data as the generated `rpk` reference instead of being typed by hand.

[,asciidoc]
----
The default is rpkval:[rpk topic create --partitions].
Use `rpkval:[rpk topic create --partitions,shorthand]` for short.
The window defaults to rpkval:[rpk ai auditlog list --since].
Every command accepts rpkval:[rpk --config-opt,shorthand] (rpkval:[rpk --config-opt,type]).
----

Rendered against `rpk-v26.2.2.json`, those lines read: "The default is -1", "Use `-p` for short", "defaults to 24h", and "accepts -X (stringArray)". For property values, use <<propval>>; for Connect fields, <<connectval>>; to name and link the command itself, <<rpkcmd>>.

=== Usage

[,asciidoc]
----
rpkval:[<rpk command> --<flag>,<field>,format=human|raw]
----

The brackets start with the command line as you type it: the command path, then the flag's long name with its dashes. The leading `rpk` is optional, and whitespace is collapsed. Each word of the path matches a command name, then an alias, so `rpkval:[rpk cluster status --format]` reads the `--format` flag of `rpk cluster info`. Dots in a flag name are allowed (`--openai-config.base-url`). For a global flag such as `--config-opt`, write `rpk` and the flag: `rpkval:[rpk --config-opt,type]`.

Write the command path and one flag only:

* An argument (`rpkval:[rpk topic create my-topic --partitions]`) is an `unknown-command` error that says to write the path without arguments.
* No flag, a value after the flag (`--partitions 3`), or a second flag is an `unknown-flag` error.
* A shorthand (`-p`) is a `shorthand-target` error whose message names the long flag: name the long flag and use the `shorthand` field.

The field comes next, `default` when it is omitted. `format=` may follow it.

The flag is looked up on that command, then in the global flags. It is never taken from a parent command: the data does not say which flags are persistent, so a parent's local flag would be a guess. A flag defined on a parent (`--schema-context` on `rpk registry`) is an `unknown-flag` error whose message names the command to write instead.

The first form of the macro is still accepted, and renders the same: the flag as the target and the command in `command=`, as in `rpkval:partitions[command=rpk topic create]` or `rpkval:partitions[shorthand,command=rpk topic create]`. Leave `command=` out for a global flag (`rpkval:config-opt[type]`). `check-reference-values --write` writes the bracket form, with the field it checked: `rpkval:[rpk topic create --partitions,default]`, or `rpkval:[rpk --verbose,default]` for a global flag.

With no flag, the brackets name a command, and the field is one of the command's own: `rpkval:[rpk topic create,usage]` renders `rpk topic create [TOPICS...] [flags]`. A flag field with no flag (`rpkval:[rpk topic create]` asks for `default`) is an `unknown-flag` error, and a command field with a flag is an `unsupported-field` error; both messages say which to write.

The `deprecated` field is gone for flags: no flag in the rpk data carries a deprecation (`deprecated_commands` covers commands only), so it could only ever say `no`. `rpkval:[... --flag,deprecated]` still renders, as `<unknown deprecated>`, with a `dropped-field` warning that says why, and never fails the build.

format::
`human` (default) or `raw`. It changes `required` and `self-hosted-only` to `true` or `false`, and `aliases` and `platforms` to a JSON array. Any other value warns and renders the human form.

The output is a `<span class="rpk-value">` with `data-rpk-command`, `data-rpk-flag` (for a flag) and `data-field` attributes. `data-field` is the canonical field, or `optional` when that is what the call asked for. A flag scraped from a plugin's `--help` also carries `data-source="help"`. The macro works inside backticks.

Help text longer than one paragraph has no inline form. Write the block form on a line of its own:

[,asciidoc]
----
rpkval::[rpk topic create,description]
rpkval::[rpk security acl list,examples]
----

It renders an open block with the roles `rpk-value` and `rpk-value-<field>`. A description is parsed as AsciiDoc, as the rpk reference renders it: code, links, and `----` listings render as they do there, with its links rewritten for the page it renders on. Examples render literally (<<value-text>>).

=== Formatting

`rpkval:` renders what pflag stores as the flag's default, which is what `--help` prints. It never humanizes: durations stay as Go writes them (`10s`, `1m0s`), and slices render as pflag prints them (`[]`, `[a,b]`). An empty string renders `""`, and booleans and numbers render as stored. It never parses a default out of a description.

=== Which rpk data a page reads

The data is an `rpk-<version>.json` attachment in a `reference` module. The docs rpk workflows publish the newest snapshot of `docs-data/rpk-v<version>.json` there. Selection follows `prop:` exactly (<<prop-version-selection>>):

[cols="1,2,2"]
|===
| Page | Dataset | When there is none

| `streaming` on main (26.2)
| Its own `rpk-v26.2.x.json`: the page's version first, then the newest in the 26.2 series
| A placeholder and the series warning

| `streaming` beta (26.3, a prerelease)
| Its own 26.3 files only. It never borrows 26.2 data
| A placeholder and the series warning

| `streaming` older versions
| Their own file
| A placeholder until one is published

| cloud-docs (`env-cloud`) and adp-docs (`env-adp`)
| The newest GA `streaming` file, then `ROOT`. The surface is Cloud
| A placeholder, and a prerelease-only or no-data warning

| Any other component
| None, never inferred
| A placeholder and the no-data warning
|===

`env-adp` borrows rpk data only: `prop:` and `propval:` still borrow on `env-cloud` alone.

=== Cloud

On a page whose surface is Cloud:

* A command or flag marked `selfHostedOnly` anywhere on its path is `unavailable`, because it is self-managed only.
* The `default` of a command whose reference description is scoped to self-managed (`descriptionScope: self-hosted`, such as `rpk shadow delete`) is `cloud-hidden`, because the behavior may differ in Cloud. Its other fields still render.
* The `description` of such a command is `cloud-hidden` too, because the reference shows it only outside `env-cloud`. On a self-managed page, the description of a command scoped to Cloud (`descriptionScope: cloud`) is `unavailable`.
* `platforms` and `linux_only_commands` are not gated: they describe the operating system, not the deployment.

On a self-managed page, a flag marked `cloudOnly` is `unavailable`, mirroring the `ifdef::env-cloud[]` the reference puts around it.

=== Failures and validation modes

Whenever no verified value exists, `rpkval:` renders `<unknown FIELD>` (class `rpk-value rpk-value-unknown`) and logs why, naming the macro call, the field, the dataset, and the file. It never renders a guessed value.

rpk-validate::
`warn` (default) logs each problem. `error` fails the build on `unknown-command`, `unknown-flag`, `shorthand-target`, `deprecated-command`, `missing-field`, `unsupported-field`, `cloud-hidden`, `unavailable`, `needs-block` (help text longer than one paragraph in the inline form) and `block-form-inline` (`rpkval::` inside a sentence). `off` silences warnings for values that render; a placeholder is still reported, because a value has no safe fallback.

These render a placeholder and warn, and never fail the build: the data gaps `no-data`, `imprecise`, `description-default` (an empty default whose description states the real one, such as `rpk debug bundle --output`), `complex-default` and `plugin-unknown`, and `dropped-field` (`deprecated` on a flag).

`deprecated-command` covers a command that is a key of `deprecated_commands`, or whose ancestor is, and its message carries the replacement. It is checked before `unknown-command`, because deprecated commands are not in the tree.

=== Plugin flags until DOC-2689

`rpk ai`, `rpk check`, `rpk connect`, `rpk k8s` and `rpk oxla` are plugins, and until they publish their own command trees (DOC-2689), the generator scrapes their flags from `--help`. A scraped flag's default is the string help printed, with its quotes, and a flag with no default means help said nothing, not that there is none. So for a scraped flag, `rpkval:` strips one pair of quotes from the default, adds `data-source="help"`, and renders `plugin-unknown` (warn only) when the default or `required` is absent.

A flag is scraped when its command is under one of those plugins, the snapshot's `plugin_flag_sources` does not record that plugin as `tree`, and the flag carries no `from_plugin: true` marker. Both markers are what the generator writes once the plugin trees land, so no change here is needed when they do.

=== Checking prose with check-reference-values

`doc-tools check-reference-values` finds hand-written flag defaults that `rpkval:` could render, and `rpk` commands and flags the data does not have. It reads both forms of `rpkval:`, and `rpkcmd:`, as macros, never as hand-written values. See <<check-reference-values>>.

== rpkcmd

This inline macro renders an `rpk` command as inline code, written as you type it, and links it to the command's generated reference page. The command is checked against the same rpk data as <<rpkval>>, and the page is found in the build, so the link follows the component that renders the page.

[,asciidoc]
----
Create the topic with rpkcmd:[rpk topic create].
Set the partition count with rpkcmd:[rpk topic create --partitions].
Check the brokers with rpkcmd:[cluster status].
Then rpkcmd:[rpk topic create,text=create a topic] for each tenant.
----

Rendered in `streaming` 26.2, the first three lines show `rpk topic create`, `rpk topic create --partitions` and `rpk cluster status` as code, linked to the `rpk topic create` page (twice) and the `rpk cluster info` page, because `status` is an alias of `info`. The last line links the words "create a topic".

=== Usage

[,asciidoc]
----
rpkcmd:[<rpk command> [--<flag>],text=<link text>]
----

The brackets hold the command exactly as you type it, aliases included, then at most one flag, long (`--partitions`) or shorthand (`-p`). The leading `rpk` is optional; the output always starts with `rpk`. For a global flag, write `rpk` and the flag: `rpkcmd:[rpk --profile]` links the `rpk` page.

Write the command path and at most one flag. An argument (`rpkcmd:[rpk topic create my-topic]`) is `unknown-command`, and a value after the flag (`--partitions 3`) or a second flag is `unknown-flag`. The command and flag resolve exactly as in `rpkval:`: names then aliases, deprecated commands before unknown ones, the command's own flags then the global flags, and never a parent's flag (`rpkcmd:[rpk registry mode set --schema-context]` is `unknown-flag`, and the message says to write `rpkcmd:[rpk registry --schema-context]`).

text::
Optional. The link text, instead of the command as code.

The output is the generated page's link around `<code class="rpk-command">`, with `data-rpk-command` (the canonical command, `rpk cluster info` for `rpk cluster status`) and, with a flag, `data-rpk-flag` (the long name). Don't wrap the macro in backticks: it already renders code, and backticks nest a second code element around the link.

The generated `rpk` pages have no anchor per flag (the Flags section is a table with no IDs), so a flag links its command's page.

[[rpkcmd-page]]
=== Which page it links

The page path comes from the command, as the `rpk` docs generator writes it: `rpk` is `rpk/rpk.adoc`, a top-level command with subcommands and every command below it are in `rpk/rpk-<top>/rpk-<path>.adoc` (`rpk/rpk-cluster/rpk-cluster-partitions-move-cancel.adoc`), and a top-level command without subcommands is `rpk/rpk-<name>.adoc` (`rpk/rpk-version.adoc`), all in the `reference` module. The macro then looks for that page in the content catalog, in this order:

. The rendering page's own component and version.
. The `streaming` component: the rendering page's version when the page is in `streaming`, else the latest version. A `streaming` page never links another `streaming` version.
. Any other component that has the page, the one with the most pages in that page's directory first, then the one with the most `rpk` reference pages. A `streaming` page that names `rpk cloud login` links cloud-docs, which publishes most of the `rpk-cloud/` pages, not adp-docs, which has more `rpk` pages but only that one `rpk cloud` page.

The rendering page is the one Antora converts, so a cloud-docs stub that includes a `streaming` page links cloud-docs pages, and an rp-connect-docs page links `streaming`. No repo or component is listed in the macro: a page that exists in the build is linked, and one that doesn't is not.

The command is checked against the rpk data the page reads for `rpkval:` (<<rpkval>>). A component that is not a Redpanda release and borrows no rpk data, such as rp-connect-docs, checks against the data of the latest `streaming` version. A `streaming` version with no rpk data of its own never borrows another release's: its commands render as plain code with the series warning.

=== Cloud

A Cloud page (`env-cloud` on its component version) links only its own component's pages. When Cloud has no page for the command, the macro renders plain code and warns, and never links Cloud readers to self-managed docs. Put such a sentence in an `ifndef::env-cloud[]` block, or link it differently in Cloud.

=== Failures and validation modes

Whenever the command can't be linked, `rpkcmd:` renders the command as plain code (`<code>`), or the `text=` value as plain text, with no link and no `rpk-command` class, and logs why, naming the macro call, the dataset and the file.

rpk-validate::
The same attribute as `rpkval:`. `warn` (default) logs each problem. `error` fails the build on `unknown-command`, `unknown-flag` and `deprecated-command`. `off` silences every `rpkcmd:` warning, because plain code still reads correctly.

These never fail the build: `no-data` (no rpk data for the page) and `no-page` (no component in the build has the page, or a Cloud page has none of its own).

=== Checking links with check-reference-values

`doc-tools check-reference-values` checks hand-written xrefs to `rpk` reference pages, reports the broken and mislabeled ones, and with `--write` replaces each exact one with `rpkcmd:[...]`. See <<check-reference-values>>.

=== Usage

[,asciidoc]
----
connectval:[<type>/<name>.<field.path>,<field>,format=human|raw]
connectval:[<type>/<name>,<field>]
connectval:[config.<field.path>,<field>]
----

The brackets start with the component and the field path together: `inputs/kafka_franz.consumer_group`, `outputs/iceberg.commit.cleanup_on_failure`. Component names have no dots, so the first dot after the type ends the name. Address an array of objects without an index (`sasl.mechanism`): the data stores one element's fields. `config.` addresses the root fields of a pipeline config (`config.pipeline.threads`, `config.http.enabled`). A component with no field path reads a field of the component itself, such as its `status`.

The type is written as rp-connect-docs paths and xrefs write it, `inputs/kafka_franz`, `rate_limits/local`, and may be plural, singular, or hyphenated (`rate-limits`, `rate_limit`). It is always explicit, so `kafka`, `http_client` and `file` are never ambiguous.

The field comes next, `default` when it is omitted. Every value macro shares one set of field names (<<value-fields>>).

The first form of the macro is still accepted, and renders the same: the field path as the target and the component in `component=`, as in `connectval:client_id[default,component=inputs/redpanda]` or `connectval:pipeline.threads[component=config]`. `check-reference-values --write` writes the bracket form, with the field it checked: `connectval:[inputs/aws_dynamodb_cdc.checkpoint_table,default]`, or `connectval:[config.pipeline.threads,default]` for a root field.

| field
| `interpolated`: the field takes interpolation functions
| `yes` or `no`

| `status`
| component
| `status`
| `stable`, `beta`, `experimental`, `deprecated`

| `category` (alias `categories`)
| component
| `categories`, comma-separated
| `Services`, `AWS`
|===

format::
`human` (default) or `raw`. It changes the yes-or-no fields to `true` or `false`, and `values` and `category` to a JSON array.

Don't wrap `values` in backticks: it already renders each value as inline code. The output is a `<span class="connect-value">` with `data-connect-component`, `data-connect-field` (for a field) and `data-field` attributes. `data-field` is the canonical field (`values` for a call that asked for `options`), or `optional` when that is what the call asked for.

A description or an example longer than one paragraph has no inline form. Write the block form on a line of its own, which parses the text into the page:

[,asciidoc]
----
connectval::[inputs/kafka_franz.consumer_group,description]
----

It renders an open block with the roles `connect-value` and `connect-value-<field>`. The strings were written for the component's own page, so off that page their links are rewritten (<<value-text>>).

=== Formatting

Connect renders what the reference prints, through `formatConnectDefault` and `connectDisplayType` in `tools/redpanda-connect/helpers/formatConnectDefault.js`, which `renderConnectFields` also calls. `[]` and `{}` render as written, a string that is already quoted renders as stored, an empty string renders `""`, and numbers and booleans render as stored. A default the reference prints as a YAML block (any other object or list) is `complex-default`: link the reference instead. An empty default whose description names the real one (`gcp_spanner_cdc` `metadata_table`) is `description-default`.

A deprecated field still renders, and the macro warns `deprecated-field`, because the Connect reference does not list deprecated fields.

=== Which Connect data a page reads

Connect versions are Connect's own (4.x), so the page's component and version never select the data. Every page reads the newest `connect-<version>.json` in the `components` module of the component named `connect` (rp-connect-docs). When more than one exists, the newest wins and the macro warns once. With no `connect` component in the build, every value is a placeholder and the warning says to add the rp-connect-docs content source to the playbook.

=== Cloud

The surface is Cloud when the page's own component version sets `env-cloud`, so a cloud-docs page that includes rp-connect-docs text is gated. On a Cloud page:

* A component that is not available in Cloud is `unavailable`. Availability comes from the translated `csvData` rows that `generate-rp-connect-info` sets on the `connect` component (GPU-only components count as available), else from the component's `cloudSupported` in the JSON. The message names the source. When neither says, the value renders and the macro warns `cloud-unknown` once.
* `introduced` is `cloud-hidden`, for a field or a component.
* The root config (`config.` or `component=config`) is never gated.
* A link in a description to a page Cloud does not have renders as its label, unlinked, with a warning (<<value-text>>).

=== Failures and validation modes

A missing value renders `<unknown FIELD>` (class `connect-value connect-value-unknown`) and logs why.

connect-validate::
`warn` (default) logs each problem. `error` fails the build on `unknown-type`, `unknown-component`, `unknown-field`, `missing-field`, `unsupported-field`, `cloud-hidden`, `unavailable`, `needs-block` (a string longer than one paragraph in the inline form) and `block-form-inline` (`connectval::` inside a sentence). `off` silences warnings for values that render; a placeholder is still reported.

These never fail the build: `no-data`, `imprecise`, `description-default`, `complex-default`, `deprecated-field` and `cloud-unknown`.

=== Checking prose with check-reference-values

`doc-tools check-reference-values` finds hand-written field defaults that `connectval:` could render, YAML comments that state a stale default, and components and fields the data does not have. See <<check-reference-values>>.

=== Registration

Registered by the `prop` macro's extension (see <<rpkval>>).

[[connect]]
== connect

This inline macro renders a Redpanda Connect component, or one of its fields, as inline code, linked to its generated reference page, and a field to its anchor on that page. The component and field are checked against the Connect data `connectval:` reads, and the page is found in the build, so the link follows the component that renders the page.

[,asciidoc]
----
Read from Kafka with the connect:[inputs/kafka_franz].
Set connect:[inputs/kafka_franz.consumer_group] to share the load.
The connect:[outputs/amqp_1.metadata] field filters the headers.
Use connect:[inputs/generate,`generate`] for test data.
----

Rendered in `connect`, the first line shows "`kafka_franz` input", linked to `components:inputs/kafka_franz.adoc`, the second `consumer_group`, linked to `#consumer_group` on the same page, and the third `metadata`, linked to `#metadata-2` on the `amqp_1` output page. The last line links its own text.

=== Usage

[,asciidoc]
----
connect:[<type>/<name>]
connect:[<type>/<name>.<field.path>]
connect:[<type>/<name>[.<field.path>],<link text>]
----

The brackets start with the component as `connectval:` takes it (<<connectval>>): the type is always written, as rp-connect-docs paths write it (`inputs`, `rate_limits`) or singular or hyphenated, because 71 names exist in more than one type. A field path follows the name, without `[]`. Root config fields (`config.`) have no reference page to link.

The default text is the component name as code and its type (`+`kafka_franz` input+`, `+`local` rate limit+`), or the field path as code. The second attribute, or `text=`, replaces it, and is rendered as written: `+connect:[inputs/generate,`generate`]+`.

The output is the page's link around `<code class="connect-component">`, with `data-connect-component` (`inputs/kafka_franz`) and, for a field, `data-connect-field`. Don't wrap the macro in backticks.

Only this short form exists. Asciidoctor matches an inline macro name anywhere in a word, so a `connect:<target>[]` form would match inside `xref:connect:components:inputs/kafka.adoc[]`.

[[connect-page]]
=== Which page and anchor it links

The page is `components:<type>/<name>.adoc`, found in the content catalog, page aliases included, in this order:

. The rendering page's own component and version. The `connect` component finds its own pages here, and Cloud finds its stubs, which declare the connect paths (`components:inputs/kafka_franz.adoc`) as page aliases. A name the reference keeps as a page alias, such as `inputs/pg_stream` on the `postgres_cdc` page, links that page.
. The `connect` component's latest version, except from a Cloud page.

A field links the id Asciidoctor generates for its heading on the published page (`+=== `batching.byte_size`+` is `batching-byte_size`). The ids are the ones docs.redpanda.com generates, with no prefix and `-` as the separator; a build that keeps Asciidoctor's own defaults (`_batching_byte_size`) needs `idprefix: ''` and `idseparator: '-'`, as `local-macro-showcase-playbook.yml` sets them. When a section earlier on the page already has that id, the field gets the next free one, as Asciidoctor numbers them: the `amqp_1` output's description has a Metadata section, so its `metadata` field is `metadata-2`, and the `jira` input's `fields` field is `fields-2`, after the page's Fields heading. The earlier sections come from the connect page's own source and the partials it includes, read from the build when it has them and from the Connect data when it does not. A field the reference does not list (a deprecated one, or one below it) links the page with no anchor, with a warning.

=== Cloud

A Cloud page (`env-cloud` on its component version) links only its own component's pages. When Cloud has no page for the component, the macro renders plain code and warns, and never links Cloud readers to self-managed docs. Put such a sentence in an `ifndef::env-cloud[]` block.

=== Failures and validation modes

Whenever the component can't be linked, `connect:` renders plain code with no link and no `connect-component` class, and logs why, naming the call, the dataset and the file.

connect-validate::
The same attribute as `connectval:`. `warn` (default) logs each problem. `error` fails the build on `unknown-type`, `unknown-component` and `unknown-field`. `off` silences every `connect:` warning.

These never fail the build: `no-data` (no Connect data) and `no-page` (no page in the build, or a Cloud page has none of its own).

=== Registration

Registered by the `prop` macro's extension (see <<rpkval>>).

[[blobl]]
== blobl

This inline macro renders a Bloblang function or method call as inline code, exactly as written, linked to its entry in the Bloblang reference.

[,asciidoc]
----
Stamp each message with blobl:[now()].
Upper-case the field with blobl:[.uppercase()].
blobl:[counter(min)] sets the first value.
Check for a substring with blobl:[.contains(),category=String Manipulation].
----

Rendered in `connect`, those link `guides:bloblang/functions.adoc#now`, `guides:bloblang/methods.adoc#uppercase`, `guides:bloblang/functions.adoc#counter` and `guides:bloblang/methods.adoc#contains-2`.

=== Usage

[,asciidoc]
----
blobl:[<function>()]
blobl:[.<method>()]
blobl:[<function>(<parameter>)]
blobl:[<call>,<link text>,category=<category>]
----

A leading dot makes a method, and parentheses without one a function. A bare name (`blobl:[now]`) works when only one kind has it; `bytes` is both, so it needs the parentheses or the dot. A name inside the parentheses is a parameter, which has no anchor of its own (each parameter table sits under a numbered `parameters-N` heading), so it links its function or method.

The methods page lists each method under its category heading. `contains`, `length` and `slice` are in two categories, each with its own description, and the second copy on the page has a numbered id (`contains-2`). `category=` picks one, by its name in any case or spacing (`String Manipulation`, `string_manipulation`); without it, the first copy on the page. The order of the categories is the order of the published `bloblang/methods.adoc` partial when the build has it, otherwise General first, Deprecated last and the rest alphabetical, which is that partial's order.

The second attribute, or `text=`, replaces the text, as in `connect:`. The output is the page's link around `<code class="bloblang-call">`, with `data-bloblang-function` or `data-bloblang-method`.

=== Which page it links

The functions page is `guides:bloblang/functions.adoc` and the methods page `guides:bloblang/methods.adoc`, found as `connect:` finds a component page (<<connect-page>>): Cloud's stubs alias those paths.

=== Cloud

The Cloud functions page leaves out the impure functions (`count`, `env`, `file`, `file_rel` and `hostname`). The data has no Cloud flag for functions, so `impure` is the gate: on a Cloud page, `blobl:` renders an impure function as plain code and warns. Methods are the same on both.

=== Failures and validation modes

connect-validate::
`error` fails the build on `unknown-function`, `unknown-method`, `unknown-parameter`, `ambiguous-name`, `hidden` (`nothing()` and `var()`, which the reference does not document) and `unknown-category`. `no-data`, `no-page` and an impure function on Cloud never fail the build.

=== Registration

Registered by the `prop` macro's extension (see <<rpkval>>).

[[value-text]]
=== Descriptions and other text values

`description`, `summary`, `examples` and `see-also` are text, rendered from its source format:

[cols="1,2"]
|===
| Source | Rendered as

| Property strings, and Connect strings while the data says `docs_format: asciidoc`
| AsciiDoc: `code`, emphasis, links, lists, admonitions, listings, tables, and `ifdef::env-cloud[]` conditionals, which apply with the page's attributes

| Connect strings once the data says `docs_format: markdown`
| Markdown, converted to AsciiDoc first: paragraphs, emphasis, code spans, links, lists, fenced code, headings, block quotes and pipe tables

| rpk descriptions
| AsciiDoc, as the rpk reference renders them: the data carries the `docs-data/rpk-overrides.json` text. A `{name}` placeholder the page does not define as an attribute, such as `+agents/{agent}/triggers/{trigger}+`, keeps its braces

| rpk examples
| Literally, as cobra prints them: paragraphs, with each indented run, and each listing between `----` lines, as a literal block. Backticks and asterisks render as written
|===

The inline form renders a text value only when it is one paragraph. Anything longer (a blank line, a list, a listing, a heading, a conditional) renders `<unknown FIELD>` with a `needs-block` warning that names the block form: the same macro with two colons, on a line of its own, such as `propval::cleanup.policy[description]`, `rpkval::[rpk topic create,description]` or `connectval::[inputs/kafka_franz.consumer_group,description]`. The block form parses the text into the page. A heading in the text renders as a discrete heading, because a section cannot open inside a block. Written inside a sentence, the block form is a `block-form-inline` error.

A Connect string was written for its component's page in `connect:components`, so a link in it is relative to that page. When the string renders anywhere else, its links are rewritten:

* `<<signal_table_name,...>>`, an anchor on the component's page, links that page's anchor.
* An xref with no component, such as `xref:components:inputs/broker.adoc[]` or `xref:guides:bloblang/about.adoc[]`, keeps pointing at the connect component. On another page in `connect`, a bare page gets its `components` module. On a Cloud page, the link stays relative to the Cloud component, where the Cloud stubs alias the connect paths (`components:inputs/broker.adoc`). On any other page it is qualified with `connect:`.
* A target the rendering page's build has no page for renders as its label, unlinked, with a warning. A Cloud reader is never linked to the self-managed docs.

A Bloblang string was written for the functions or methods page in `connect:guides`, so `bloblval:` rewrites its links the same way, with that page in place of the component's page and `guides` in place of `components`: `<<round,...>>` in a method description links `guides:bloblang/methods.adoc#round`.

An rpk description was written for its command's reference page in the component the rpk data came from (`streaming`, for a Cloud or Agentic Data Plane page too), so its links are relative to that page. `rpkval:` and `rpkval::` rewrite them for the page that renders the description:

* An xref to a command's page, such as `xref:reference:rpk/rpk-cloud/rpk-cloud-mcp-install.adoc[]`, links the page `rpkcmd:` would link for that command (<<rpkcmd>>), fragment included: the page's own component first, so a Cloud page links its Cloud stub and an Agentic Data Plane page its own `rpk` page, then `streaming`, then any other component with the page. A Cloud page links only Cloud pages.
* `xref:./rpk-redpanda-tune-list.adoc[]` names a page beside the command's page, and is resolved there first. `<<disk_irq,...>>` is an anchor on the command's page, and links it, unless the description renders on that page.
* Any other xref with no component, such as `xref:manage:security/authorization/acl.adoc[]`, stays as written when the rendering page's component version has the page, and is otherwise qualified with the data's component and version (`26.2@streaming:manage:...`). On a Cloud page it is never qualified.
* An xref that names a component, such as `xref:connect:streaming:about.adoc[]`, stays as written.
* A target the rendering page's build has no page for renders as its label, unlinked, with a warning, as for Connect strings. An unlinked target with an empty label renders as the command in backticks, or as the page title or file name.

Property descriptions and examples link with module-qualified xrefs that resolve wherever the property reference itself renders, so they are not rewritten.

[[check-reference-values]]
== Checking prose: check-reference-values

`npx doc-tools check-reference-values` runs three checks over a docs checkout and writes one JSON and one Markdown report. Each kind selects its data exactly as its macro does, from the repo and any `--lender` checkouts, unless `--data-file` names it.

properties:: The `generate migrate-property-values` scan, unchanged. See <<propval>>.
rpk:: Every `rpk` invocation in a shell listing block and every backticked `rpk ...` span in prose is parsed as `rpk` parses it. An unknown subcommand is `unknown-command`, with a suggestion (`movement-cancel` suggests `move-cancel`); a flag no command on the path defines is `unknown-flag`; a deprecated command is a warning that carries its replacement. A flag default stated in prose ("`--limit` defaults to 50") or in a Default table column is compared with what `rpkval:` renders for the nearest command on the page that defines the flag. `rpkcmd:[...]` and both forms of `rpkval:` count as macros, never as hand-written values: a flag in `rpkcmd:[rpk topic create --partitions]` is a mention of that command's flag, and `rpkcmd:[rpk topic create]` names the command later flag mentions belong to.
rpk links:: Every hand-written xref to a page under `reference:rpk/` in prose and tables is resolved as the scanned component renders it, by Antora's rules (a target with no component is the page's own component and version, a component with no version is its latest) and through the `page-aliases` the `rpk` pages declare. The scan reads the `rpk` pages of the repo and every `--lender`:
+
* `broken-link` (reference error): the page does not exist there, or the target has no `.adoc` extension and no fragment, which Asciidoctor renders as a link to an anchor on the same page. The note says what `rpkcmd:` would link instead, or that Cloud has no page for the command.
* `link-label-mismatch` (reference warning): the label's leading `rpk ...` names another command than the page documents (the label `rpk profile` on a link to the `rpk profile create` page). A label of just `rpk` names the tool and is not checked.
* `exact`: the label is the command in backticks, with at most one known flag, the target is the page `rpkcmd:` would link (<<rpkcmd-page>>), and the xref has no fragment and no pinned version. `--write` replaces it with `rpkcmd:[...]`, in prose or a table cell, when the build has an `rpk-<version>.json` attachment for `rpkcmd:` to link with. Without one, `rpkcmd:` would render plain code, so the finding is proposed only, even when `--data-file` names the data the scan checks against.
* `link-target-not-loaded` (unverifiable): the target is in a component or version the scan did not read. Pass that checkout with `--lender`.
+
On a self-managed scan, a line inside `ifdef::env-cloud[]` renders only where Cloud includes the file, so its links are checked as the one `--lender` that sets `env-cloud` renders them, and not checked without one. Nav files listed in `antora.yml`, the generated `rpk` pages and partials, stub pages, and xrefs shown as code are not checked. The report counts the links in `linksBroken`, `linksMislabeled`, `linksReplaceable` and `linksNotLoaded`.
connect links:: Every hand-written xref to a Connect component page (`components:<type>/<name>.adoc`), a field anchor on one, or the Bloblang functions or methods page is judged on every component that renders the file: the scanned component for a page, or for a partial one of its pages includes, and each `--lender` that includes the file, such as a cloud-docs stub that includes an rp-connect-docs page. An xref with no component resolves in the rendering component, page aliases included, so the same xref can work in `connect` and break in Cloud. A line in `ifndef::env-cloud[]` is judged off Cloud only, and one in `ifdef::env-cloud[]` on Cloud only. An include with `tag=` or `tags=` renders only the lines in those tag regions, and an include line inside an `env-cloud` conditional renders only on the surfaces the conditional keeps. A Cloud stub's path that Cloud now aliases to the type's about page (a component Cloud removed) is not the component's page. The anchors are the ones `connect:` and `blobl:` compute (<<connect-page>>, <<blobl>>), plus the page's own section ids.
+
* `broken-link` (reference error): the page does not exist on a rendering component, or the anchor is not on the page there: a field the reference does not list, an impure function on Cloud, a hidden function, or a numbered `parameters-N` heading. A field anchor that is off by its number names the right one.
* `link-label-mismatch` (reference warning): the label's backticked name is another component, field, function or method than the target, or calls it another type (`+`redis` cache+` on the `redis` rate limit page). A name the target page declares as a page alias (`pg_stream` on `postgres_cdc`) is the same component.
* `exact`: the label is just the name (`+`kafka_franz`+`, `+`kafka_franz` input+`, `+`write_mode`+`, `+`now()`+`, `+`fold` method+`, `+method `catch`+`), and on every rendering component the target is the page and anchor the macro links. `--write` replaces it with `connect:[...]` or `blobl:[...]`, keeping the label as the link text when the macro's own would differ, and adding `category=` for a second method copy. Without a `connect-<version>.json` attachment in the build, the finding is proposed only.
* `link-target-not-loaded` (unverifiable): no page in the scan renders the line (a partial only a component outside the scan includes), or the target component is not in the scan. Pass that checkout with `--lender`. A scan of rp-connect-docs with no Cloud `--lender` reports every link in a partial or a page's `single-source` tag region this way, because Cloud may render it. Pass the cloud-docs checkout to check them.
+
Nav files, generated pages, stub pages and xrefs shown as code are not checked, and the SQL reference (`modules/reference/pages/sql/`), whose backticked SQL functions share Bloblang names, is never read for Bloblang links. The report counts the links in `linksBroken`, `linksMislabeled`, `linksReplaceable` and `linksNotLoaded`.
unlinked mentions:: The docs link a term on its first mention in a document, so the first mention on a page of something a link macro links, written with no link, is an `unlinked-mention` finding:
+
* `rpk-command`: a backticked `rpk` command in prose or a table cell, with or without flags (`+`rpk topic create`+`, `+`rpk cluster info --detailed`+`), that resolves to a command with a reference page for the scanned component, found as `rpkcmd:` finds it (<<rpkcmd-page>>). A Cloud page reports only the commands Cloud has a page for. A span with an argument (`+`rpk topic consume hello-world`+`) is an example to run, not a mention, but a placeholder (`+`rpk topic consume <topic_name>`+`) is not an argument, and a span the data does not resolve is a reference finding instead.
* `connect-component`: a Connect component named with its type, `+`kafka_franz` input+`, or with no backticks when the name has an underscore, `kafka_franz input`. The type must be the component's.
* `bloblang-function` and `bloblang-method`: `+`now()`+`, `+`.uppercase()`+`, `+`count` function+` or `+`index` method+`, in Connect content only: rp-connect-docs, and pages in a `connect` directory elsewhere, never the SQL reference, whose `+`count()`+` is SQL. A name the data has as the other kind, or not at all, is not a mention.
+
A page is judged as it renders: its own lines, with each `include::` replaced by the lines it includes, in order. Includes are followed into nested includes, the lines a `tag=` or `tags=` selects (`!` negations too; a wildcard includes every line), a target built from attributes when each is set at that point, and other components the scan has as a `--lender` (a cloud-docs stub's `include::streaming:...`). An include of a component the scan did not load is not followed. `ifdef::` and `ifndef::` keep or drop lines by the attributes set at that point: the component's `antora.yml` attributes (`env-cloud` on Cloud), then the attribute entries of the page and what it includes, so a partial's `ifndef::env-kubernetes[]` lines are not on a page that sets `:env-kubernetes: true`. `ifeval::` keeps its lines, and an attribute only the playbook or Antora sets (`page-*`) reads as unset.
+
Only the first mention of a target on a page is reported, and none when the page links the target anywhere, before or after: an xref to its page (any fragment, a Cloud stub's path, or a page alias), or `rpkcmd:`, `connect:` or `blobl:`. A mention in a partial is reported at the partial's own file and line, where a writer fixes it, when it is the first unlinked mention on at least one page that includes the partial; the finding's `pages` and note name those pages. When every page that shows it links the target or mentions it first, it is not reported. A partial no loaded page includes, or a line no loaded page shows, is judged on its own file: its first mention, in a file that links the target nowhere. So a scan without the cloud-docs checkout judges the lines only Cloud shows as a file, and a cloud-docs page that includes `streaming:` content is judged without that content unless the docs checkout is a `--lender`. A mention is never read in a block, a heading, a block title, a description list term, a table header row (`%header`, `options="header"`, or the implicit header: a first row on one line followed by a blank line), a link label or a macro (`xref:`, `link:`, a URL, `+{attr}[label]+`, `<<id,label>>`), and never in nav files, release, upgrade or migration notes, generated pages, the target's own page or its partials, or a line under `// value-check: ignore`, after which the next mention is the first. Each finding names the page the macro would link and proposes the macro: `rpkcmd:[rpk topic create]` when the span is the command and at most one flag, and `connect:[...]` or `blobl:[...]` with the mention's text as the label when it is not what the macro renders (`+connect:[processors/mapping,`mapping` Processor]+`). The report counts them in `unlinkedMentions` and `unlinkedMentionsByKind`.
connect:: Every pipeline config in a YAML listing block or an examples file is walked from its root keys. An unknown component is `unknown-component`, an unknown field is `unknown-field`, and deprecated components and fields are warnings. A YAML comment that states a default ("# Optional (default: "benthos")") is example output that `matches` or is `stale`. A callout ("<3> ... The default is `1024`.") or a sentence that states a field's default is compared with what `connectval:` renders. A `connect:[...]` link names the component and field a stated default belongs to, and `bloblval:` and `connect:` values are macros, never hand-written values.

Statuses are propval's, plus `reference` for a thing the data does not have. `--fail-on mismatch` (the default) fails on mismatches, reference errors, and stale rpk and Connect examples; `any` also fails on exact, equivalent and unset values and on reference warnings, which catches every hand-written value a macro could render. Unlinked mentions never fail at these levels: `links` fails on everything `any` does and on unlinked mentions. Plugin flags scraped from `--help` never fail, and neither do findings in release notes, upgrade notes or Connect migration guides. A `// value-check: ignore` comment line suppresses the findings on the next line, or in the block it sits directly above. Exit 0 means nothing failed, 1 that something did, and 2 that the check could not run.

`--write` applies only exact matches in the same sentence (or a Connect callout) that name one target, never in a table, block or YAML, never a scraped plugin flag or an empty default, and never in a file that may be single-sourced into Cloud where the macro would render a placeholder. An exact `rpk` or Connect xref is replaced in prose or a table cell: `rpkcmd:`, `connect:` and `blobl:` link the same page from the page's own component, and on Cloud render plain code where the xref would be broken. Each replacement is kept only when the line renders the same visible text before and after, through the real macros.

Turning a mention into a link changes the page, so `--write` leaves unlinked mentions as written unless `--write-links` is given as well; `--write-links` without `--write` is a setup error (exit 2). With both, each reported mention that has a proposed macro becomes that macro, under the same render check, so its text stays exactly as written. A mention that is not reported, because each page that shows it already links the target or mentions it first, is never written. A mention whose span has a flag value, a placeholder, or a second flag, is reported and never written: link the command page by hand.

----
npx doc-tools check-reference-values --docs-dir . --data-file docs-data/rpk-v26.2.2.json --lender ../rp-connect-docs
npx doc-tools check-reference-values --docs-dir ../cloud-docs --lender ../docs ../rp-connect-docs --data-file ../docs/docs-data/rpk-v26.2.2.json
npx doc-tools check-reference-values --docs-dir ../rp-connect-docs --lender ../docs ../cloud-docs --data-file ../docs/docs-data/rpk-v26.2.2.json --write --write-links

== glossterm

The `glossterm` inline macro provides a way to define and reference glossary terms in your AsciiDoc documents.

NOTE: This macro is a customized version of https://gitlab.com/djencks/asciidoctor-glossary[`asciidoctor-glossary`].

=== Usage

Use the `glossterm` inline macro to reference a term within the text of the document:

[,asciidoc]
----
glossterm:my term[myDefinition]
----

It takes two parameters:

term::
The term to be defined.

definition (optional)::
The definition of the term. If the term is defined in the https://github.com/redpanda-data/docs-site[`shared` component] or the `local-terms` object of the `antora.yml` file, you can omit the definition as it will always be replaced by those definitions.

=== Configuration options

glossary-log-terms (optional)::
Whether to log a textual representation of a definition list item to the console.

glossary-term-role (optional)::
Role to assign each term. By default, glossary terms are assigned the `glossary-term` role, which gives them the class `glossary-term` in generated html.

glossary-links (optional)::
Whether to generate links to glossary entries.
By default, links to the glossary entries are generated from the glossary terms. To avoid this, set the attribute to `false` as either asciidoctor configuration or a header attribute.

glossary-page (optional)::
Target page for glossary links. By default, links are generated to the same page as the glossary term. To specify the target page, set this attribute to the resource ID of a page where the `glossary` block macro is used.

glossary-tooltip (optional)::
Whether to enable tooltips for the defined terms. Valid values are:
- title: This uses the browser built-in `title` attribute to display the definition.

- true: This inserts the definition as the value of the attribute `data-glossary-tooltip`.

- data-<attribute-name>​: This inserts the definition as the value of the supplied attribute name, which must start with `data`.

The last two options are intended to support js/css tooltip solutions such as tippy.js.

=== Registration

[,yaml]
----
asciidoc:
  extensions:
    - '@redpanda-data/docs-extensions-and-macros/macros/glossary'
----

== iceberg-explorer

This macro registers an `[iceberg-explorer]` block that emits a version-aware mount point for the interactive Iceberg Mode Explorer:

[,html]
----
<div class="iceberg-explorer-mount" data-iceberg-explorer="1" data-version="26.2">
  <p class="iceberg-explorer-fallback">Interactive Iceberg Mode Explorer. If this text is still here...</p>
</div>
----

The block renders the container only. The explorer UI and its translation engine live in the docs-ui bundle, which hydrates the mount point, so the block is inert unless the site uses a docs-ui build that includes the explorer. This is the same "macro emits container, docs-ui hydrates it" handshake used by the Redpanda Connect component metadata block.

Until the explorer module replaces the container's contents, the fallback paragraph is visible. It is ordinary markup rather than `<noscript>` on purpose: the failure readers are most likely to hit is JavaScript running normally on a site whose UI bundle has no explorer module, and a browser hides `<noscript>` in that case, leaving a zero-height blank space with no explanation.

The page's component version (`page-version`, falling back to `page-component-version`) is stamped onto the mount point as `data-version` so the UI can load the engine build that matches the doc version. If neither attribute is set, `data-version` is omitted.

Antora derives both attributes from the component version and locks them, so a page header cannot set them: an unversioned component (`version: ~`, which is what this repo's preview site uses) emits no `data-version`, and docs-ui falls back to its own version detection.

=== Mount contract

docs-ui must hydrate on the `data-iceberg-explorer` attribute (`[data-iceberg-explorer]`), never on a class name that matches the block name.

Asciidoctor turns an unrecognized block style into a CSS class. A site that uses `[iceberg-explorer]` but whose playbook does not register this macro still publishes `<div class="openblock iceberg-explorer">`, with the author's JSON body dumped onto the page as a code listing. If the explorer module hydrated on `.iceberg-explorer`, that accident would render as a working-looking explorer filled with built-in sample data, the author's defaults silently discarded, and no error anywhere to trace it back to the missing playbook entry.

Only this macro can emit a data attribute, so:

* `data-iceberg-explorer` is the mount contract, and its value is the contract version (`1` today). Bump it only if the emitted attributes change shape.
* `iceberg-explorer-mount` is a styling hook, not a mount signal.

The constants are exported (`MOUNT_ATTRIBUTE`, `MOUNT_CONTRACT_VERSION`, `MOUNT_CLASS`, `MOUNT_SELECTOR`) so docs-ui and the tests can assert against one definition.

=== Usage

```asciidoc
[iceberg-explorer]
--
--
```

Set the initial configuration with the `config` attribute:

```asciidoc
[iceberg-explorer,config="key:mode=binary;value:mode=binary"]
--
--
```

Or pass a JSON object as the block body to supply author-defined defaults:

```asciidoc
[iceberg-explorer]
----
{
  "config": "value:mode=schema_latest"
}
----
```

The explorer module reads only the `config` key and renders its own sample schema and record. Other keys are forwarded verbatim in `data-defaults` and ignored, so do not document author-supplied schemas or records as supported until docs-ui reads them.

The JSON is attribute-escaped and emitted as `data-defaults`. The body must be a JSON *object*: `JSON.parse()` also accepts scalars and arrays, and docs-ui reads keys off the parsed value, so a bare `123` is as unusable as a syntax error. If the body is not a JSON object, the macro logs a warning that names the page, omits `data-defaults`, and still renders the mount point.

The block accepts an open (`--`), listing (`----`), literal, or pass body. It is not registered for the paragraph context, because the processor replaces the block with the mount point: registering paragraphs would delete the prose under a stray `[iceberg-explorer]` line from the published page.

|===
| Attribute | Description

| `config`
| Initial configuration string. Emitted as `data-config`. Falls back to the `config` key of the JSON body.

| `height`
| Minimum height for the container, emitted as an inline `min-height` style. A bare number is treated as pixels (`height=400` becomes `min-height:400px`). Otherwise the value must be a CSS length in `px`, `rem`, `em`, `vh`, `vw`, or `%`; any other value is rejected with a warning rather than interpolated into the style attribute.

| `engine-base`
| Optional base location for the translation engine build, emitted as `data-engine-base`. It must be a root-relative path on the docs site, such as `/_/engine/26.2`, because docs-ui loads a script from it. Any other value (an absolute or protocol-relative URL, a relative path, backslashes, or control characters) is ignored with a build warning. docs-ui falls back to its own default when this is absent, so set it only to pin a specific engine build.
|===

=== Registration

[,yaml]
----
asciidoc:
  extensions:
    - '@redpanda-data/docs-extensions-and-macros/macros/iceberg-explorer'
----

=== docs-ui dependency

This block is half of a two-repo handshake and does nothing on its own. The explorer UI and its translation engine ship in docs-ui, so the block requires a docs-ui release that includes the explorer module. On a site built with a bundle that lacks the module, the block renders the container and its fallback paragraph, nothing more.

Order of operations before an author uses the block on a published page:

. Merge and publish this package, so consumers can resolve the macro.
. Release a docs-ui bundle that includes the explorer module, with hydration keyed on `[data-iceberg-explorer]` (see <<Mount contract>>).
. Add the macro to each consuming playbook's `asciidoc.extensions` (`redpanda-data/docs`, `cloud-docs`). Registering it in this repo's `local-antora-playbook.yml` covers only this repo's preview site.

Until step 2 lands, a page that uses the block shows the fallback paragraph rather than an explorer. That is deliberate: it is visible, so a missing or outdated UI bundle looks broken rather than looking like a page with nothing on it.
